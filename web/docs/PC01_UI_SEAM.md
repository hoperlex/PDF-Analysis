# PC-01 UI seam — frozen at Gate A by session `A5`

> Seam `S9` of `docs/program/P02_SEAMS.md` §1. Producer: `A5`. Consumers: `B7`, `B8`.
>
> This document is what `B7` and `B8` build on and never edit. It fixes the route URLs,
> the shared components and hooks that exist, the transport surface, the query-key
> namespaces, the polling contract, and the ownership line between the two Gate B
> frontend sessions.
>
> To change something frozen here: write the failing test that shows the current shape
> does not serve your slice, hand both to the integrator, and do not edit this file or
> `web/src/shared/**` from a Gate B session. A shape change reaches both consumers, so
> it is announced, not merged quietly — the same rule `P02_SEAMS.md` §10 states for the
> backend seams.

## 0. What `A5` delivered, and what it deliberately did not

Delivered: a pinned toolchain with a committed lockfile, the app shell and composition
root, the generated typed API client, the shared primitives, and the guards that keep
all of it honest.

**Not delivered, on purpose: any product screen.** Projects, upload, run progress,
findings, evidence, decisions and export are `B7` and `B8`. The four routes exist and
render a placeholder that names the module each is waiting for.

## 1. Ownership — the line between `B7` and `B8`

`web/src/app/**`, `web/src/_app/**`, `web/src/shared/**`, `web/openapi/**`,
`web/scripts/**`, `web/tests/guards/**`, `web/tests/contract/**` and every web root
config file belong to `A5` and are frozen at the Gate A commit. Neither Gate B session
edits them. Shape your slice as an addition; if it cannot be, that is a seam request.

| Tree | Owner |
|---|---|
| `web/src/_pages/projects/**`, `_pages/project-detail/**`, `_pages/run/**` | `B7` |
| `web/src/widgets/project-list/**`, `widgets/upload-panel/**`, `widgets/run-progress/**` | `B7` |
| `web/src/features/create-project/**`, `features/upload-document/**`, `features/start-run/**` | `B7` |
| `web/src/entities/project/**`, `entities/document-version/**`, `entities/audit-run/**` | `B7` |
| `web/src/_pages/review/**` | `B8` |
| `web/src/widgets/finding-list/**`, `evidence-viewer/**`, `decision-panel/**`, `decision-history/**`, `export-panel/**` | `B8` |
| `web/src/features/open-evidence/**`, `record-verdict/**`, `append-comment/**`, `export-run/**` | `B8` |
| `web/src/entities/finding/**`, `finding-observation/**`, `expert-decision/**` | `B8` |
| `web/tests/unit/<area>/**` | the session that owns `<area>` |

**Neither session owns `web/src/app/**`.** The four route files are written; a session
that needs its screen mounted replaces the single placeholder expression in its route
with a delegation and changes nothing else in that file. Two sessions editing route
files is the collision this rule exists to prevent — if both need a change to the same
route file, that is a seam request, not a merge.

`B7` and `B8` share the run: `B7` owns run progress, `B8` owns everything under review.
The shared surface between them is `queryKeys.runs` (§6) and the `RunStatus` model. `B8`
reads run state to decide whether export is offered; it does not poll (§7).

## 2. Route URLs — frozen

| URL | File | Screen | Owner |
|---|---|---|---|
| `/` | `src/app/page.tsx` | redirect to `/projects` | `A5` |
| `/projects` | `src/app/projects/page.tsx` | project list and create | `B7` |
| `/projects/{project_uid}` | `src/app/projects/[project_uid]/page.tsx` | one project: upload, start run | `B7` |
| `/projects/{project_uid}/documents/{document_uid}` | `.../documents/[document_uid]/page.tsx` | one document, its versions | `W19-SHELL` |
| `/projects/{project_uid}/versions/{version_uid}` | `.../versions/[version_uid]/page.tsx` | one published version: manifest, runs, start a run | `W19-SHELL` |
| `/projects/{project_uid}/runs/{run_id}` | `.../runs/[run_id]/page.tsx` | run progress | `B7` |
| `/projects/{project_uid}/runs/{run_id}/review` | `.../runs/[run_id]/review/page.tsx` | findings, evidence, decisions, export | `B8` |

Every address in this table is built by `routes` in `@/shared/lib`, and never by a
template literal at a call site. An address that exists in four places can be wrong in
three of them, and the property these routes have to keep — **a URL pasted into a fresh
tab renders** — is a property of the string.

Route parameter names are the contract's path parameter names exactly — `project_uid`,
`run_id`. They are opaque `<prefix>_<ULID>` strings; nothing in the UI parses one, and
`version_ordinal` is never accepted as a path parameter.

Review is a child of the run, not a sibling: a finding is only meaningful against the run
that produced it.

**Amended 2026-09-18 by `W19-SHELL` under `DEBT_REGISTER.md` D-16.** This section used to
read *"there is no route for a document version"*, and that sentence was the defect. With
no address for a document and none for a version, everything below the project list could
be reached only by having just created it in the same browser session: `W15-RUN` measured a
project page on a fresh load making **zero** API calls and reporting *"No version published
in this session"* over a project whose documents, versions, runs and decisions had all
survived in PostgreSQL and the store. The two rows above are the repair, and they became
possible when `W18-SEAL` added `listDocuments`, `listVersions` and `listRuns` under ruling
`R-5`.

The review screen still opens version *content* through `streamDocumentVersionContent`;
that is unchanged. What is new is that the version itself has an address.

**Through this surface a document has exactly one version today** (`W18-SEAL` §2:
`uploadDocument` declares no `document_uid`), so the document screen lists one row and the
project screen links past it, straight to the version. The document address exists anyway,
because `document_uid` is a value this product prints — a CSV column, a field of every
`DocumentVersion`, the subject of a `404` envelope — and an identifier a product prints and
cannot open is `D-16` in miniature.

## 3. Shared components — `@/shared/ui`

Import from `@/shared/ui`. Never from a file inside it.

### 3.1 The five mandatory states

Every list, panel and viewer renders one of these when it has no content. No slice
invents a sixth.

| Component | Props | When |
|---|---|---|
| `LoadingState` | `what?: string` | a request is in flight |
| `EmptyState` | `title`, `detail?`, `action?` | the request succeeded and there is genuinely nothing |
| `ErrorState` | `title`, `detail?`, `correlationId?`, `onRetry?`, `retryLabel?` | the request failed |
| `UnsupportedState` | `title`, `detail?` | the input is outside the PC-01 envelope |
| `NotApplicableState` | `title`, `detail?` | the question does not apply to this object |

`ErrorState` is the only one with an action. Pass `onRetry` **only** when the failure is
retryable — the transport decodes `retryable` from the envelope, so branch on that, not
on the HTTP status. `UnsupportedState` and `NotApplicableState` have no action by design:
offering "try again" for a 31-page PDF teaches the user the wrong thing.

Always pass `correlationId` on `ErrorState` when you have one. It is the only handle an
operator has on the diagnostic record, and the contract puts `X-Correlation-Id` on every
response precisely so the UI can show it.

### 3.2 The two badges, and why they are two

| Component | Props | Value set |
|---|---|---|
| `RunStateBadge` | `state: RunState`, `providerMode?: 'live' \| 'recorded'` | `created`, `queued`, `running`, `validating`, `published`, `partial`, `failed`, `cancelled` |
| `StageStatusBadge` | `status: StageStatus`, `errorCode?: string \| null` | `succeeded`, `partial`, `failed`, `skipped` |

**`succeeded` is legal on a stage row and illegal on a run badge.** The success terminal
of an `AuditRun` is `published`; `succeeded` is a `StageResult` status on a different
aggregate. `RunStateBadge` takes the generated `RunState`, so `<RunStateBadge state="succeeded" />`
does not compile. A repository-wide ban on the word would be wrong — `succeeded` is
correct on a stage row — which is why the rule is stated per component here and why
`P3-WEB-00` scopes its `rg` check to the run vocabulary only.

Only contract state names are rendered. No slice writes "in progress", "done" or "OK".

`providerMode` belongs on the run badge rather than in a caption elsewhere: a recorded
run is not evidence of a live one, and the two must be distinguishable at a glance.

### 3.3 Frame

| Component | Props |
|---|---|
| `PageShell` | `title`, `subtitle?`, `actions?`, `children` |
| `RoutePlaceholder` | `screen`, `route`, `awaitingModule`, `owner` |

`RoutePlaceholder` is `A5`'s stand-in and disappears as each slice lands. It is neither a
loading state nor an error state: nothing was requested and nothing failed.

### 3.4 Widget props `B7` and `B8` still own

`EvidenceViewer`, `DecisionPanel`, `ExportPanel`, `FindingList`, `DecisionHistory`,
`ProjectList`, `UploadPanel` and `RunProgress` are **not** in `shared/ui`. They are widget
slices owned by `B7`/`B8` and their props are declared by their owners. What is frozen
here is the data they receive: the generated contract models of §4, the query keys of §6,
and the state vocabulary of §3.2. A widget takes contract models and callbacks; it does
not take a raw `Response`, a URL, or a hand-written error string.

The export panel has **no polling contract**, because the export endpoint is synchronous
(§7).

## 4. The transport seam — `@/shared/api`

One import path for everything: `import { ... } from '@/shared/api'`. A slice never
imports from `@/shared/api/generated`, never sees a `Response`, never constructs a URL and
never writes an error string by hand.

### 4.1 Generated, and never hand-edited

`web/src/shared/api/generated/**` is produced by `npm --prefix web run api:generate` from
`contracts/api/v1/openapi.json`. Four files, all carrying a do-not-edit header:
`types.gen.ts`, `operations.gen.ts`, `client.gen.ts`, `index.ts`.

It exports: every one of the 43 component schemas as a type; a `*_VALUES` const and union
for every string enum; a `*_PATTERN` string for every patterned identifier, so a form can
validate without hand-copying a regex; one `<Operation>Input` and `<Operation>Result` per
operation; the `OPERATIONS` runtime descriptor table; and one function per operation.

### 4.2 The twelve client functions

```
createProject(input, options?)                 POST   /projects                                   write
listProjects(input, options?)                  GET    /projects
uploadDocument(input, options?)                POST   /projects/{project_uid}/documents            write
getDocumentVersion(input, options?)            GET    /versions/{version_uid}
streamDocumentVersionContent(input, options?)  GET    /versions/{version_uid}/content              -> Blob
startRun(input, options?)                      POST   /runs                                       write
getRunStatus(input, options?)                  GET    /runs/{run_id}
listRunFindings(input, options?)               GET    /runs/{run_id}/findings
getFinding(input, options?)                    GET    /findings/{finding_uid}
appendDecision(input, options?)                POST   /findings/{finding_uid}/decisions            write
listDecisionHistory(input, options?)           GET    /findings/{finding_uid}/decisions
exportRunCsv(input, options?)                  GET    /runs/{run_id}/export.csv                   -> Blob
```

Every one returns `ApiResponse<T> = { data, status, correlationId }`. Input shape:

```ts
{
  path?: { ... },          // required when the URL has parameters
  query?: { ... },         // only the parameters the contract declares
  body?: ...,              // for the four writes
  idempotencyKey: ...,     // required on the four writes, typed as required
  correlationId?: ...,     // optional; the edge assigns one when absent
  headers?: { Range?: ... } // only streamDocumentVersionContent
}
```

### 4.3 Idempotency — one key per intent

The four writes take a required `idempotencyKey`. Mint it with `newIdempotencyKey()` when
the user expresses the intent — presses "create", chooses a file, clicks "accept" — and
keep it for the lifetime of that intent, **including every retry**.

* `idempotency_key_in_progress` — the same key and payload is still executing. Retry the
  **same** key. Never mint a new one: a fresh key is a second command.
* `idempotency_key_reuse` — the same key arrived with a different payload. A terminal,
  user-visible conflict. Nothing was created and nothing is resubmitted.
* `idempotency_key_stale` — the recorded outcome is gone and is not guessed.

### 4.4 Failures

Three things can be thrown, all extending `ApiFailure` with `correlationId` and
`retryable`:

| Thrown | Meaning |
|---|---|
| `ApiError` | a decoded `ErrorEnvelope` with a code from the closed catalog; carries `errorCode`, `status`, `envelope`, `details` |
| `UnrecognizedApiError` | a well-formed envelope with a code outside the catalog. An **explicit** state: render "unrecognized error" with the correlation id, retry nothing |
| `TransportError` | no decodable envelope at all — network failure, abort, non-JSON body |

`retryable` always comes from the envelope, which the contract pins to the catalog value
for the reported code. **Never infer it from the HTTP status.**

Branch with `hasErrorCode(error, 'not_found')`, `isIdempotencyInProgress(error)`,
`isIdempotencyKeyReuse(error)`. `PC01_ERROR_CODES` is the ten-code subset a PC-01 screen
must be able to render; the generated `ErrorCode` is the full twenty-code catalog, and
`P02_SEAMS.md` §9.4 records why the other ten have no PC-01 producer. The subset carries
no partial-specific refusal: under `OD-11` a `partial` run **is** exported, and a run
whose terminal does not publish a result is refused with `state_transition_not_allowed`.

### 4.5 Run state helpers

`TERMINAL_RUN_STATES`, `NON_TERMINAL_RUN_STATES`, `isTerminalRunState(state)`,
`EXPORTABLE_RUN_STATES`, `isExportableRunState(state)`, `stageCarriesError(status)`.

The terminal/non-terminal split is a partition of the contract enum, proved at compile
time and again by a contract test. `isExportableRunState` encodes `OD-11`: `published` and
`partial` export; a non-terminal run and `failed` do not, and `cancelled` is unreachable in
PC-01. The server remains the authority — this only decides whether the control is offered.

### 4.6 CSV

`CSV_COLUMNS` is the frozen seventeen-column list of `P02_SEAMS.md` §6, in order, checked
against that document by a contract test. `CSV_ENCODING` states the bytes: UTF-8 **with a
BOM**, comma, CRLF, RFC 4180 quoting, null projected as the empty string. `csvFileName(runId)`
suggests a download name; the server's `Content-Disposition` wins if it sends one.

The browser never builds a CSV from cached data.

## 5. Configuration — `@/shared/config`

`getApiBaseUrl()` throws `MissingConfigurationError` when `NEXT_PUBLIC_API_BASE_URL` is
unset or blank. **There is no localhost default**, in code or anywhere else: a default
would let a build appear configured while talking to nothing. `hasApiBaseUrl()` exists for
a diagnostic screen, not for a fallback.

`getInstanceLabel()` returns a cosmetic label or `null`.

This is the only module in `web/` that reads `process.env`, enforced by a guard test. No
secret, S3 endpoint, bucket name or credential enters the web tier — `NEXT_PUBLIC_*` is
compiled into the browser bundle, so anything placed there is public by construction.

## 6. Query keys — frozen namespaces

Build every key by calling `queryKeys.*`. Never write an array literal.

| Key | Shape | Primary user |
|---|---|---|
| `queryKeys.projects.all()` | `['projects']` | `B7` |
| `queryKeys.projects.list(cursor?, limit?)` | `['projects','list',{cursor,limit}]` | `B7` |
| `queryKeys.projects.detail(projectUid)` | `['projects','detail',uid]` | `B7` |
| `queryKeys.versions.detail(versionUid)` | `['versions','detail',uid]` | `B7` |
| `queryKeys.versions.content(versionUid)` | `['versions','content',uid]` | `B8` |
| `queryKeys.runs.all()` | `['runs']` | `B7` |
| `queryKeys.runs.detail(runId)` | `['runs','detail',id]` | `B7` |
| `queryKeys.runs.findings(runId, filters?)` | `['runs','findings',id,filters]` | `B8` |
| `queryKeys.findings.detail(findingUid)` | `['findings','detail',uid]` | `B8` |
| `queryKeys.findings.decisions(findingUid)` | `['findings','decisions',uid]` | `B8` |

`projects`, `versions`, `runs`, `findings` are the only legal first segments. Invalidation
targets a prefix: appending a decision invalidates `queryKeys.findings.decisions(uid)` and
`queryKeys.findings.detail(uid)`, and — because the verdict projection appears in the
finding list — `queryKeys.runs.findings(runId)`.

There is **no global domain store.** The query client in `_app` is the only cache. PC-01's
state lives on the server; a second copy of it in the browser is a second source of truth
that will disagree with the first.

## 7. Polling — frozen interval and backoff

| Value | Setting |
|---|---|
| initial interval | 2000 ms |
| backoff factor | 1.5 |
| maximum interval | 15000 ms |
| wall-clock deadline | none |

Schedule: 0, 2000, 3000, 4500, 6750, 10125, 15000, 15000, … (`pollDelayMs(attempt)`
computes it, and is pure so a test can assert the schedule without waiting for it).

`pollRunStatus(input, options)` is the **only** run-progress loop. It stops on any terminal
state, on abort, and on a non-retryable failure; a retryable failure is absorbed and the
loop continues at the next interval. No other slice polls the run endpoint.

There is no wall-clock deadline on purpose: the stop condition is the run's own terminal,
and inventing a timeout would invent a failure the contract does not define.

**Nothing else polls.** PC-01 has no WebSocket and no server-sent events, and the export
endpoint is synchronous — no export resource, no export identity, nothing to poll. The
export panel holds no polling state.

These numbers are `A5`'s, not an upstream owner decision: no P02 document declares a
polling interval. Changing them is a change to `shared/config/polling.ts` and to this
section, in one commit.

## 9. Boundaries a Gate B session will run into

* **Downward imports only**: `app`/`_app` → `_pages` → `widgets` → `features` → `entities`
  → `shared`. ESLint rejects an upward import.
* **Slice public API only**: `@/entities/project`, never `@/entities/project/model/store`.
* **One `fetch` in the application**, inside `src/shared/api`. ESLint and a text-scanning
  guard both enforce it; the scanner exists because ESLint can be silenced with a comment
  and does not run in the build.
* **`process.env` only in `src/shared/config`.**
* **No object key, bucket name, storage URL or credential anywhere in `web/`.**

Each of these has a guard that has been shown to fail: see `web/tests/guards/**`.

## 10. Known limits of this seam

* No authentication, no roles, no tenancy. One configured local reviewer label,
  server-side, per `OD-12`; the UI never sends an author identity.
* One appearance. No theme system, no dark mode, no i18n — the AR corpus is Russian, the
  shell is not localized.
* No browser PDF rendering approach is pinned here. `OD-09` covers it and `B8` takes it
  with its evidence viewer; the transport side is settled — `streamDocumentVersionContent`
  returns a `Blob` and accepts a `Range` header, and there is no presigned link and no
  redirect, because a URL into object storage is the internal address the contract forbids
  in a response and would outlive the request that authorized it.
* No Playwright configuration. `e2e:pc01` is reserved and fails explicitly; `A5` did not
  add `@playwright/test`, whose install downloads browsers and would make
  `npm --prefix web ci` non-hermetic. `P3-QA-01` adds the dependency with its suite.
* `needs_manual_review` is in the closed verdict union and has no PC-01 producer.
  `revoke` is in the decision-event union and no PC-01 client offers it.

## 11. A contract defect that was found here, and is now repaired

`A5` reported that `FindingDetail` composed `Finding` — which is `additionalProperties:
false` — with a branch adding `latest_comment` and `decision_event_count`. Under JSON
Schema 2020-12 the closed branch rejected both, so `FindingDetail` could not validate
carrying the two fields it exists to add. `A5` verified it with a Draft 2020-12 validator
and correctly left it unrepaired, because `contracts/api/v1/**` was not its to write.

**It is fixed.** Session `A7-FIX` restated `FindingDetail` as one standalone closed object
carrying `Finding`'s properties plus the two additions, leaving `Finding` untouched. The
integrator verified the repaired document independently: the payload carrying both fields
raises no `additionalProperties` error; an unknown property is still rejected on
`FindingDetail` and on `Finding`; and `Finding` still refuses the detail-only field, so the
distinction this endpoint draws survives. No `allOf` remains anywhere in the document. The
reasoning, including the two shapes that were built and rejected, is in
`docs/program/tasks/P3-API-01.md`.

**What this means for `B8`.** The generated TypeScript did not change — it was always the
shape you want: `FindingDetail = Finding & { decision_event_count?: number;
latest_comment?: string | null }`. Build against it. **The earlier warning in this section
told you not to validate the detail response against the contract document. That warning is
withdrawn: it was true only of the broken document and would now steer you away from a check
that works.**
