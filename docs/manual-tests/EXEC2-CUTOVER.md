# EXEC2-CUTOVER — переход исполнителей с Primary/Standby на правила и откат

Руководство оператора для стенда. Задача `EXEC2-CUTOVER-01`, ADR-0026, решение 17. Переход выполняет администратор,
**один раз, вручную, после выкладки этапа 3**. Сам по себе деплой ничего не переключает: режим остаётся `legacy`
(Primary/Standby), пока администратор не подтвердит переход.

Все проверки выполняются на синтетических данных. Автоматические тесты этой задачи написаны и не запускались (`R-149d`), поэтому
этот прогон на стенде — первое исполнение перехода на настоящей базе.

## Что нужно знать до начала

- **Режим** хранится в базе (`legacy` по умолчанию, `rules`). Каждая смена режима — отдельная запись журнала режима, номера идут
  подряд без пропусков. Режим меняется только записью; откат — это тоже запись.
- **Группа** — набор взаимозаменяемых исполнителей одной модели. Переход создаёт **группу из одного участника** на каждый тип
  задач: участник — подключение, которое сейчас указано как Primary, в его **текущей ревизии**.
- **Standby показывается и не переносится.** Резервное подключение не становится участником ни одной группы. При переходе на
  правила резерва нет: правила его не используют. Если резерв нужен, добавьте его вручную вторым участником группы той же модели
  (новая ревизия группы) — после перехода, не вместо него.
- **Один и тот же тип задач, один раз.** У каждого из шести типов задач (`text_analysis`, `comparison_pair_check`,
  `comparison_sheet_changes`, `comparison_spec`, `comparison_report`, `comparison_stage_review`) либо есть правило, либо нет. Тип
  задач без правила при режиме `rules` **не** идёт через старый Primary: старт такой задачи отказан (`503 dependency_unavailable`,
  `no_rule_for_work_kind`).
- **Работа, уже принятая, не переезжает.** См. раздел «Что происходит с работой в очереди и в процессе».

## Предусловия

- Вы вошли как администратор (`admin`). Остальные роли получают `403`.
- Стенд обновлён до версии с контрактом не ниже 1.16.0 и головой миграций не ниже `0048` (на 2026-11-04 — `0049`); запишите версию, коммит и режим в начале протокола:

```text
candidate_commit:
contract_version:
migration_head:
routing_mode_before:   legacy
tester:
started_at:
```

- Для каждого типа задач, который вы собираетесь перевести, подключение-Primary: не в архиве, **проверено зондом на текущей ревизии**
  (карточка подключения: последний зонд `ok`), для `pull` — раннер на связи. Предпросмотр зонд не проверяет (в контракте для этого
  нет статуса): если зонд не пройден, группа будет создана, а её участник не будет выбираться — работа будет ждать. Проверьте зонды
  заранее.
- Желательно сделать переход в тихое время, без стартов «на лету»: старт, который прочитал режим до подтверждения, идёт по старому
  маршруту; после подтверждения — по правилу. Останавливать очередь не требуется.

## Шаг 1. Предпросмотр

**Где.** «Исполнители» → «Правила» → «Перейти на правила» (панель показывает предпросмотр и ничего не записывает). То же через API:
`GET /api/v1/executor-routing/preview`.

**Что видно.** Ровно шесть строк, по одной на тип задач, и контрольный `preview_digest`. Для каждой строки:

| Статус | Что значит | Что делать |
|---|---|---|
| `ready` | Есть Primary, он не в архиве, у него есть ревизия, и этот релиз обслуживает его вид. Показаны подключение, его **текущая** ревизия, модель, биллинг и предложенное имя группы. | Проверить строку (список ниже). |
| `no_route` | У типа задач нет маршрута. | После перехода у него не будет правила, старт будет отказан. Либо заранее создайте группу и правило вручную («Группы», «Правила»), либо примите это. |
| `incompatible` | Маршрут есть, но группу из него сделать нельзя. Причина: `connection_archived` (Primary в архиве), `no_revision` (нет ревизии), `kind_not_served` (релиз не обслуживает этот вид). | Строку нельзя подтвердить. Исправьте подключение (разархивировать нельзя — создайте новое подключение и назначьте его маршрутом в режиме `legacy`) и запросите предпросмотр заново. |

**Проверьте каждую `ready`-строку.**

1. Тип задач и Primary — те, что вы ожидали.
2. Ревизия подключения — текущая (а не та, с которой маршрут был назначен).
3. Модель и биллинг — те, что вам нужны для этого типа задач (группа однородна, биллинг и ставки одной группы совпадают).
4. Предложенное имя группы вас устраивает. Имя не должно совпадать (без учёта регистра) с именем действующей группы; сервер уже
   предлагает свободное имя, добавляя « (2)», « (3)». Имя можно изменить при подтверждении.
5. Если у строки показан **standby** — помните: он не станет участником. Решение о резерве — после перехода (см. выше).
6. Зонд Primary на текущей ревизии — `ok` (см. предусловия).

Запишите `preview_digest`. **Запись:** `PASS / FAIL / BLOCKED`, фактический результат, ссылка на безопасное свидетельство.

## Шаг 2. Подтверждение

**Действие.** Отметьте строки, которые переводите (из `ready`), проверьте имена групп и подтвердите. Панель отправляет
`POST /api/v1/executor-routing/mode` с `mode: rules`, `preview_digest` из шага 1 и подтверждённым `mapping` (тип задач и имя
группы). Ключ идемпотентности создаётся на каждое подтверждение.

**Что происходит — одной транзакцией:**

1. сервер берёт блокировку журнала режима и заново считает предпросмотр под блокировкой подключений;
2. если его контрольное значение не равно вашему — отказ, ничего не создано;
3. для каждого выбранного типа задач создаются группа, её первая ревизия с одним участником и правило;
4. записывается событие режима `rules` с контрольным значением и списком созданного;
5. всё это пишется в журнал событий (`executor.group_created`, `executor.routing_rule_set`, `executor.routing_mode_changed`).

Типы задач, которые вы **не** выбрали, не получают группу и правило. Если для такого типа правило было создано вручную раньше, оно
остаётся в силе.

**Ожидаемо.** Ответ `200`: режим `rules`, список созданных групп и действующие правила. Раздел «Назначения» заменяется
«Правилами»; маршруты Primary/Standby остаются как история (только чтение).

**Отказы и что делать.**

| Ответ | Причина | Что делать |
|---|---|---|
| `409`, `preview_stale` | После предпросмотра изменился маршрут, ревизия подключения, имена групп или статус строки. | Запросите предпросмотр заново, перечитайте строки, подтвердите снова. Ничего не создано. |
| `409`, `routing_mode_unchanged` | Режим уже `rules` (например, другой администратор подтвердил раньше). | Ничего не делать; проверьте шаг 3. Если нужен ещё один переход — сначала откат. |
| `409`, `group_name_in_use` | Имя занято действующей группой. | Выберите другое имя. Ничего не создано (в том числе группы, созданные до отказа в этой же транзакции). |
| `422`, `mapping_entry_not_ready` | Выбрана строка, которая не `ready`. | Уберите её из подтверждения. |
| `422`, `mapping_required` / `preview_digest_required` | Не передано подтверждение или контрольное значение. | Повторите через панель. |
| `422`, `model_not_pinned` | Модель подключения больше не в списке закреплённых. | Исправьте ревизию подключения (шаг 1) и повторите. |
| `403` | Не администратор. | Войдите администратором. |

Запрос с тем же ключом и тем же содержанием повторяется как тот же ответ и ничего не пишет; тот же ключ с другим содержанием —
отказ идемпотентности. Два одновременных подтверждения: выигрывает одно, второе получает `routing_mode_unchanged`.

**Запись:** `PASS / FAIL / BLOCKED`, ответ, `mode_event_id`.

## Что происходит с работой в очереди и в процессе

- **Run, уже запущенный или стоящий в очереди с явным подключением, пресетом или по старому маршруту** (режим «зафиксировано при
  старте»): ничего не меняется. Он идёт на своей ревизии подключения до конца, как до перехода.
- **Run на источнике `environment`:** группы он не поддерживает; не затронут.
- **Новый старт после подтверждения без выбора селектора** («Автоматически (по типу задачи)»): принимается по правилу своего типа
  задач, ждёт исполнителя (`pending`) и привязывается к участнику группы в момент выдачи. Явное подключение, пресет и именованная
  группа работают как раньше.
- **Работа, принятая правилом или группой, ждёт устойчиво:** пока участник занят, ждёт без ограничения по времени; если все
  участники не на связи дольше `AUDITMANAGER_GROUP_OFFLINE_WAIT_SECONDS` (по умолчанию 1800 с), завершается с `no_executor_online`.
  Причина ожидания видна в очереди и на экране Run. Это относится и к заданиям сравнения: воркер отдельным проходом (рядом с проходом
  по Run) держит их ожидание верным — пишет `runner_offline`, `executor_at_capacity` или снимает ожидание, когда какой-то участник
  может принять задание, — и завершает задание с `no_executor_online` только если `runner_offline` держится **непрерывно** дольше
  предела. Раннер, вернувшийся даже на один проход, сбрасывает отсчёт. Каждое задание завершается так же, как завершил бы его
  собственный обработчик метода (для `stage_review` — вместе с запуском, шагом и единицами; для отчёта — вместе со строкой отчёта).
  Приостановленное и уже завершённое задание проход не трогает.
- **Точная причина «раннер не в сети».** Слово `runner_offline` покрывает любой случай, когда ни один участник группы не может
  принять работу. Экран Run и экраны задания сравнения в этом случае читают ёмкость группы (`GET /executor-groups/{id}/capacity`)
  и пишут, что именно не так: «ревизия подключения изменилась — группу нужно пересобрать», «подключение в архиве»,
  «подключение не обслуживается», «проверка связи не пройдена», «агент офлайн». Ёмкость описывает **текущую** ревизию группы, а
  работа ждёт на той, на которой её приняли: если они разные, экран пишет «работа принята на предыдущей ревизии группы; ниже —
  состояние текущей ревизии» и затем причины участников текущей ревизии (если они что-то объясняют) или что состояние текущей
  ревизии причины ожидания не показывает; о том, что обслужит новая ревизия, экран ничего не утверждает. Предел ожидания — `AUDITMANAGER_GROUP_OFFLINE_WAIT_SECONDS`
  (по умолчанию 30 минут для всех случаев, `R-149`); экран говорит «по истечении лимита ожидания (по умолчанию 30 минут)», не
  считает и не показывает время конца и не обещает конца для приостановленной работы. Контракт не менялся.
- **После привязки** работа остаётся на своём участнике: повтор попытки идёт на нём же, неопределённый исход (`outcome_unknown`)
  никуда не переотправляется.
- **Задания сравнения** принимаются по правилам типа задач `comparison_*` так же; уже принятые до перехода идут как раньше.
  До первого обращения к модели экран задания показывает группу и плановую модель («подключение будет выбрано при первом
  обращении к модели»), после — фактическое подключение и модель.
- **Цена одна.** Задание сравнения привязывается к участнику при первом обращении, и ставки, по которым дано согласие
  (снимок ставок ревизии группы), должны совпадать со ставками, по которым оценивается участник сейчас (замок поставщика), как это
  делает Run; то же проверяется при каждом следующем обращении привязанного задания. Если замок поставщика изменился после создания
  ревизии группы, операции, которые берут согласие и заявляют `422` в контракте, **отказываются сразу**: запуск (`start*`), продолжение
  (`resume*`), повтор (`retry*`) и оценка правок листов (`estimateComparisonAiSheetChanges`) — `422 analysis_input_invalid`,
  `details.reason: cost_estimate_binding_changed` (существующий зарегистрированный отказ — то же слово, что у Run), на экране «тарифы
  группы устарели — пересоберите группу». Согласие, которое первое же обращение отказало бы, не берётся, и новое согласие не
  зацикливается. Операции без `422` в контракте так не отвечают: оценки проверки пар, описания листа и спецификации
  (`estimateComparisonAiPairCheck`, `estimateComparisonSheetDescription`, `estimateComparisonSpecification`) считаются по снимку группы,
  как раньше, и отказывает уже следующий запуск; завершение правок листов (`finishComparisonAiSheetChanges`) проходит, а первое же
  обращение задания к модели отказывает как `consent_stale`. Если расхождение возникло уже после согласия, обращение отказано как
  `consent_stale`: задание встаёт на паузу `route_changed` (у непривязанного задания ещё и `needs_reconsent`; у привязанного ожидания
  нет), ничего не пересчитывается молча. Замок, который больше не закрепляет модель группы, даёт `executor_route_missing` раньше
  проверки ставок. Выход — новая ревизия группы (она копирует ставки замка) и новое задание.
- **`import-env` после перехода.** Пока режим `rules`, маршрут «Назначения» закрыт, и команда
  `python -m auditmanager.executors import-env` подключение создаёт, но маршрут не ставит и пишет об этом в stderr (режим `rules`,
  маршрут не задан, подключение нужно добавить в группу и в правило). Код возврата `0`, если зонд прошёл, `3`, если нет.
  Повторный запуск ничего не меняет.

## Шаг 3. Проверка после перехода

Выполните по порядку.

1. **Режим.** «Правила» (или `GET /executor-routing-rules`): режим `rules`, у каждого переведённого типа задач — своё правило и своя
   группа. Журнал режима: событие 1, `rules`.
2. **Группы.** «Группы»: по одной на переведённый тип, ревизия 1, один участник — ожидаемое подключение и ревизия.
3. **Ёмкость.** Для каждой группы откройте ёмкость (`GET /executor-groups/{id}/capacity`): участник годен (`eligible`) и не имеет
   причины `probe_not_ok`, `runner_offline`, `revision_changed`. Если причина есть — запустите зонд на подключении или поднимите
   раннер и перепроверьте.
4. **Старый маршрут закрыт.** Попытка изменить маршрут («Назначения», либо `PUT /executor-routes`) отвечает `409`,
   `routing_mode_rules`; список маршрутов читается.
5. **Старт без селектора.** Запустите анализ на синтетическом документе с выбором «Автоматически (по типу задачи)»: в очереди
   видно ожидание исполнителя, затем привязку к участнику; в статусе Run — «плановая модель» до выдачи и «фактическая модель и
   подключение» после.
6. **Тип без правила.** Старт типа задач, который вы не переводили (или `no_route`), отказан с `no_rule_for_work_kind`. Это ожидаемо.
7. **Старые способы.** Старт с явным подключением или пресетом по-прежнему проходит.
8. **Журнал.** Есть события `executor.group_created`, `executor.routing_rule_set` по числу типов и одно
   `executor.routing_mode_changed` (`from_state: legacy`, `to_state: rules`).

Помните: `allow_client_documents` в этой версии не проверяется (`R-149a`, `D-291`); ёмкость выше единицы и группы — только для
тестовых данных, пока это не закрыто.

**Запись:** по каждому пункту `PASS / FAIL / BLOCKED`, фактический результат.

## Откат на Primary/Standby

**Когда.** Если шаг 3 не прошёл и причину не устранить сразу, либо нужно вернуть старый маршрут.

**Действие.** «Вернуться к основному и резервному подключению» и подтверждение (панель предупреждает, что принятая работа остаётся на своих группах).
Через API: `POST /api/v1/executor-routing/mode` с `{"mode": "legacy"}` — без контрольного значения и без `mapping`. Другого
подтверждения контракт не требует: явный запрос режима `legacy` и есть подтверждение.

**Что происходит.** Записывается одно событие режима `legacy` и событие журнала. Ни одна группа, ревизия, правило и ни одна
принятая работа не изменяются и не удаляются.

- **Принятая правилом или группой работа** (в ожидании или уже привязанная) доделывается на **своей ревизии группы** и на своём
  правиле. Она не читается по старому маршруту и не переносится на него.
- **Новые старты** без селектора снова идут по Primary/Standby, как до перехода. Standby используется только при старте и с
  событием `audit_run.standby_used`.
- **«Назначения»** снова доступны: маршруты можно менять.
- **Группы и правила** остаются видимыми. Правила не действуют, пока режим `legacy`.

**Ожидаемо.** Ответ `200`: режим `legacy`, `groups` пуст, `rules` — те же, что были. Повторный запрос `legacy` — `409`,
`routing_mode_unchanged`.

**Повторный переход.** Новый предпросмотр предложит имена с « (2)», потому что старые группы ещё действуют; подтверждение
добавит **новые** правила (номер 2 для каждого типа), а старые группы перестанут быть названы правилом и их можно будет архивировать.

**Откат релиза.** Откат самого слияния (revert) допустим только в режиме `legacy`: сначала откат режима по этому разделу.

**Запись:** `PASS / FAIL / BLOCKED`, ответ, `mode_event_id`, проверка, что новый старт без селектора идёт по Primary/Standby.
