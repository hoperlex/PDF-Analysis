**Gate lane:** `gate-w37a`, ports 56150 / 59750 / 59751. **Logs:** `/root/w37-logs/d57-*`.

`D-57`: `queryKeys.runs.detail(runId)` was filled with a bare `RunStatus` by the run

`QueryClient`. Neither half was a type error, because the key carried no type at all.

---

## 1. Which shape the key carries, and why

**The key holds the bare `RunStatus`. The review screen unwraps at the transport
boundary.** The brief left the decision open in both directions; three things decide it,
and only the third is an aesthetic preference.

**1. Every consumer wants a run, and no consumer wants the envelope.** Four sites read
this entry — the poller's `useState` initialiser, the poller's effect, the run widget
through `useRunStatus`, and the review screen's header. They read `.state`,
`.provider_mode`, `.diagnostic_observation_count`, `.stages`. Nothing reads `status` or
`correlationId`, which are the only things the envelope adds. Carrying the envelope
everywhere would make four sites write `.data` so that one call site could keep a value
none of them uses.

**2. The tree had already decided, in the other direction, and `runs.detail` was the one
key that departed from it.** `versions.detail` is written bare by
`useUploadDocument` (`setQueryData(queryKeys.versions.detail(uid), version)`) and read by
`useDocumentVersion`, whose `queryFn` ends `return response.data;`. That is exactly the
arrangement this repair gives `runs.detail`. Choosing the envelope would have made the two
`detail` keys disagree in order to fix one key disagreeing with itself.

**3. The envelope is a property of a call, not of a resource.** A cache key names a
resource. `{ data, status, correlationId }` names *one HTTP exchange* that happened to
produce it, and the same resource arrives from `startRun`'s 202 body with no envelope at
all — which is precisely why `useStartRun` wrote the bare model and could not have written
anything else without inventing a status code.

The counter-argument the brief names is real and it loses: `queryFn: getRunStatus(...)`
returns the envelope naturally, so the bare model costs one `await` and one `.data` in one
place. That place is `runStatusQueryOptions`, and it is the boundary where a transport
detail is supposed to stop.

## 3. What makes the collision impossible to repeat

**Two mechanisms, because the type system carries most of it and not all of it, and the
split is measured.**

### The part the type system carries

`queryKeys.runs.detail` now returns
`DataTag<readonly ['runs','detail',RunId], RunStatus>`. `@tanstack/query-core` 5.102.8
types both `getQueryData` and `setQueryData` through `InferDataFromTag`:

```
getQueryData<TQueryFnData = unknown, TTaggedQueryKey extends QueryKey = QueryKey,
             TInferredQueryFnData = InferDataFromTag<TQueryFnData, TTaggedQueryKey>>
            (queryKey: TTaggedQueryKey): TInferredQueryFnData | undefined;
```

So both halves of `D-57` stop compiling. Proved on fixtures by a real `tsc`, not by
restating the type in a test:

```
writes-envelope.fixture.ts(18,53): error TS2345: Argument of type '{ data: RunStatus;
  status: number; correlationId: string | null; }' is not assignable to parameter of type
  'Updater<NoInfer<RunStatus> | undefined, NoInfer<RunStatus> | undefined>'.
reads-envelope.fixture.ts(19,17): error TS2339: Property 'data' does not exist on type
  'RunStatus'.
```

The second is `runQuery.data?.data`, character for character.

**The explicit type argument is the other half of why this was never a type error**, and it
is now banned across every key, not only this one: `getQueryData<RunStatus>(key)` displaces
the tag and type-checks against any entry at all. Both read sites in `use-run-status.ts`
lost their `<RunStatus>`; the guard forbids the sequence
`getQueryData<...>(queryKeys....)` anywhere in `web/src`.

### The part it does not carry, named rather than papered over

**`useQuery` ignores the tag in `@tanstack/react-query` 5.102.8.** `InferDataFromTag`
appears in `query-core`'s build and **nowhere** in `react-query`'s; `useQuery`'s three
overloads infer `TQueryFnData` from the `queryFn` and never consult `TQueryKey`'s tag. That
is exactly the route the review screen took, so a tag alone would have left the defect's
own path open.

`web/tests/guards/query-key-shape.guard.test.ts` §2 closes it as a source rule: exactly one
module may name this key as a `queryKey` (`entities/audit-run/api/run-status-query.ts`),
its `queryFn` states `Promise<RunStatus>` rather than inferring it, and the guard asserts
against `node_modules` that `react-query` still lacks `InferDataFromTag` — **so the premise
expires loudly.** The guard says in its own text to delete §2 rather than keep it if a
later version carries the tag into `useQuery`.

### The part that would otherwise have been enforced by a command the gate does not run

**`make gate`'s frontend half is `npm --prefix web test`, which is `vitest run`, which
transforms TypeScript with esbuild and does not typecheck.** Every rule the tag enforces —
including the `setQueryData` in `useStartRun`, which is the one write site no behaviour
test reaches — would have been enforced only by `npm run typecheck` and `next build`,
neither of which the gate runs. A regression at any of them would have reached a green
gate.

So the guard runs `tsc --noEmit --incremental false` over `web/` as one case, four seconds.
**This is deliberately broader than `D-57`** — it reddens on any type error in `web/` — and
the integrator should know it is a new obligation the gate did not previously carry. It is
the only thing that makes "the type system carries it" true of the gate rather than of a
developer's editor. Mutation `M-6` below is the proof it was needed.

## 8. Premises of the brief measured and found false

**1. `features/start-run/api/use-start-run.ts` does not exist.** The file is
`features/start-run/model/use-start-run.ts`. The brief and `DEBT_REGISTER.md` D-57 both say
`api/`. The slice has no `api/` directory at all — `index.ts`, `model/`, `ui/`. A session
that opened the named path would have found nothing, which is §12's own location mistake in
a different directory.

**2. "Four write sites and one read site" is not what the tree holds.** Measured at
`b0e5c07`, in `web/src`: **two** sites write (`use-run-status.ts:79`,
`use-start-run.ts:38`), **three** read (`use-run-status.ts:43`, `:59`, `review-page.tsx:124`)
and **one of the readers is also the second writer** — `review-page.tsx:74`'s `useQuery`
fills the key with whatever its `queryFn` returns, which is the entire defect and is not a
`setQueryData` anywhere. Four is the count of **test seeding sites**
(`styles/screens.ts:94`, `run-progress.test.ts:39`, `forms-and-pages.test.ts:174`,
`run-terminal-reason.test.ts:34`). The distinction matters for the repair: a guard that
watched `setQueryData` would have caught neither the defect nor its return.

**3. "A finished run is polled forever" understates it.** The rendered consequence at
`b0e5c07` is a `TypeError` in `stageRows` before any polling decision is reached (§2). A
reviewer returning to the run screen meets a screen that does not render, not one that
renders and keeps asking.

**4. "The strongest available repair is a typed key" — half true, and the half that is
false is the half `D-57` lives in.** The tag governs `getQueryData`/`setQueryData`. It does
**not** reach `useQuery` in 5.102.8, which is the only mechanism by which the review screen
ever filled the key. A typed key alone would have left the defect's exact path open while
looking like a complete repair.

**5. "TanStack Query supports this; establish what this version does" — and what it does
is not what the gate sees.** The typed key is enforced by `tsc`, and `make gate` does not
run `tsc`: its frontend half is `vitest run`. Three of this repair's four write sites are
guarded only by a command that was outside the gate until §3's last paragraph put it in.

**6. `web/tests/unit/screens/harness.ts` cannot reach the poller stopping, and the brief
says it is how to reach both.** The harness renders one static pass and states in its own
header that it cannot run a `useEffect`; `polling` is set to `false` inside the effect.
What one pass *can* reach is the `useState` initialiser and everything downstream of the
reading, which is why `D-57.2` is asserted as the rendered `data-run-activity="stopped"`
plus the stop condition's own value, and not as a `polling` flag.

**7. The two suites that already render these screens are blind to this defect.**
`rendered-language.guard.test.ts` renders every screen and reads every sentence and stayed
**green** under `M-3`, the defect's exact shape. So the brief's framing that a session
"misread it" is generous to the instruments: `W32-SEE` saw the empty branch with its own
eyes and had no test that disagreed with the conclusion it drew. It wrote the correct
diagnosis into a comment in that guard, and the comment is the only thing that carried it.

**8. `D-57`'s own check command is narrower than the defect.**
`grep -n "runs.detail" <two files>` names the two files but not
`features/start-run/model/use-start-run.ts`, which is the third `web/src` site and the one
that seeds the key on the ordinary path from "start a run" to "review it". A row that names
two of three sites is how `D-4` was closed early.

## 9. Risks and known limitations

1. **The whole-project `tsc` case is a new gate obligation.** It is 4 seconds and it will
   redden on any type error in `web/`, including one introduced by another stream. That is
   intended (§3) but it is a widening, and the integrator may prefer to move it to a
   `Makefile` step it owns rather than leave it inside a guard suite. Stated here because
   it is the kind of thing that should be a decision and not a surprise.
2. **`runs.findings`, `findings.detail`, `findings.decisions` still hold envelopes.** One
   writer and one reader each, all inside `ReviewPage`, so none is `D-57`'s shape; but they
   are untagged, and a second consumer for any of them would reopen the class. They were
   left alone because tagging them would bake the envelope into keys that probably should
   not carry one, and that is a decision beyond this row.
3. **`versions.content` holds an envelope too**, for the same reason and with the same
   caveat; its consumers live outside this task's `allowed_paths`.
4. **Nothing here proves the browser journey.** The assertions are on
   `renderToStaticMarkup` output. No click target, button text or rendered sentence
   changed, so `tests/e2e/pc01/journey/manifest.json` should be unaffected — but the
   journey itself was not driven, and `MEMORY: frontend-battery-cannot-see-the-journey`
   applies.
5. **`useQuery`'s blindness to the tag is a fact about 5.102.8 and is asserted against
   `node_modules`.** An `npm ci` that changed that version reddens the premise check rather
   than silently invalidating §2, which is the intended failure mode.
