## 6. The residue that is not a machine guarantee

**Re-pointing a legacy stage name from one existing canonical stage to another existing
canonical stage passes every referential-integrity check in this family, and this review
does not and cannot claim otherwise.** Every reference stays resolvable, the identifier
sets are unchanged, no stage is orphaned, and Gates A, B, C and D all stay green. It is
a **semantic** change, and it belongs to semantic review — the `PD-02` reviewer reading
the 62 recorded `rationale` strings, and, where the meaning of a stage boundary moves,
the repository owner — not to a machine gate.

`AnalysisReferentialIntegrityTests.test_remapping_a_name_to_another_existing_stage_stays_resolvable`
asserts the residue exists rather than pretending it is closed: it performs such a remap
in memory and confirms that everything still resolves. Detecting it mechanically would
mean restating all 62 name→stage pairs inside the gate, i.e. duplicating the artifact
under check as a second normative mapping table, which this task's non-goals forbid.
`contracts/analysis/v1/README.md` states the same residue, and
`W0.3_ratification_integration.md` records that a later remap is a semantic change even
if referential-integrity gates pass. All three statements agree; this report adds no
fourth.

### 7.1 The task file's required test was unsatisfiable — **closed by the integrator before this round was assigned**

**This defect is closed and nothing is routed from it.**
`docs/program/tasks/W0-QA-01.md:117` now reads
`git status --porcelain -uall -- tests/contract docs/program/reviews` with an explicit
**containment** expectation — no path outside the two owned ones, the empty result
accepted — and the task file records that the integrator made the correction before this
round was assigned, along with the reasoning below. Both the `-uall` form and the
containment semantics were what §7.1 asked for; asking again would route work already
done. Measured on today's tree, both the task file's command and this section's
historical form print exactly the two owned paths and exit `0`.

What follows is the historical record of the defect, kept because §11 refers to it as
the fourth one-directional gate found in `W0.3` and because the shape recurs.

The form that was specified was:

```text
git status --porcelain -- tests/contract docs/program/reviews
```

with the expectation of *exactly two lines*, `?? tests/contract/test_cp00_candidate.py`
and `?? docs/program/reviews/W0-QA-01.md`. That expectation cannot be met.
`docs/program/reviews/` did not exist at the candidate commit, so while this task ran it
was a wholly untracked directory, and `git status` under its default
`--untracked-files=normal` **collapses a wholly untracked directory to a single directory
entry**. The output observed then — both files are tracked from `qa_evidence_commit`
onward, so this is the historical record of the defect, not today's status:

```text
?? docs/program/reviews/
?? tests/contract/test_cp00_candidate.py
```

12. **`tested_candidate_digest` is recomputed — over the commit that froze it, and no
    further.** Every earlier form of this item was wrong, and its wrongness is the reason
    the field went four rounds unchecked. It said the tree the value describes "stops
    existing the moment the results are written into it, so it cannot be recomputed after
    the fact by anyone", and then that the recomputed `evidence_bundle_digest` depending
    on it meant "a value naming a tree that never existed cannot sit there unnoticed".
    Both claims are false. The recipe blanks only the field being computed, so the value
    is exactly the digest of the tree at the commit that froze it, and Git keeps that
    tree forever. And dependence is not verification: an independent reviewer built a
    complete, content-correct ratification carrying `deadbeef…` as
    `tested_candidate_digest`, sealed in the order the manifest's own recipe prescribes,
    and every check stayed silent while 140 tests passed. Making the two digests move
    together never checked that the tested value named a real tree.

    What is checked now, in two halves that are not interchangeable and neither of which
    is sufficient alone. **Half one** (`_tested_digest_problems`): the value must be
    frozen at a commit — the oldest consecutive commit of the manifest carrying it both
    at the top level and in the current round's entry — and must reproduce as the digest
    of *that commit's tree*. A fabricated value fails twice: it is frozen at no commit at
    all, and a manufactured one would not reproduce. The manifest never has to record its
    own hash; history supplies it. **Half two** (`_post_freeze_delta_problems`): half one
    is green however far the working tree drifts afterwards, because the freeze commit is
    immutable — so at ratification the delta between the frozen tree and the tree in front
    of you must lie inside `POST_FREEZE_DELTA_CEILING` plus the round's own declared
    acceptance evidence, and anything else voids the round.

    **The honest limit.** Neither half proves the acceptance streams actually ran against
    the frozen tree. Half one proves the value names a tree this repository can produce;
    half two proves nothing unlicensed has moved since. A stream that reported `PASS`
    without executing, or executed somewhere else and reported here, is outside what any
    arithmetic in this module can reach — it is the manual acceptance stream's evidence
    and the integrator's discipline, exactly as item 9 records.

    Each is anchored on a distinctive literal that must be present at the reviewed

    prose in `ARCHITECTURE_LINT_RULES.md` is marked `removal_only`, because the only
    positive signal available — `GATE-E` itself — is already in the document three times

    evidence is precisely the degeneracy round six removed. What guards that entry instead
    is `must_still_contain: ("GATE-E",)`: not evidence, a guard against satisfying the

    module itself. It is now live and
    `test_gutting_the_probe_description_is_caught_by_must_still_contain` fails when it is
    made dead again (§11.12). The residual limit stands: for this entry the module proves
    the stale sentence is gone and the probe is still described, and nothing more.
14. **The external record is trusted for the fact of ratification, not for its

15. **Where a Git command this module runs can land, and what still decides it.** This
    item has been rewritten twice because it twice stated a guarantee a reviewer then
    falsified. The history is kept, because the pattern is the finding.

    * Round eight stated the rule as "nothing writes to the repository under review,
      asserted at a single door." Round nine falsified it: with a legitimate `mkdtemp`
      sandbox root — the door's path check passing cleanly — `GIT_DIR` on the calling
      process retargeted the write to another repository entirely. `git -C` sets only
      the directory discovery starts from. **A guard validates its argument; only
      measuring the destination establishes a property of the destination.**
    * Round nine then stated that the destination "is not determined by anything in the
      calling process's environment" and that the environment "can no longer redirect
      either write regardless of what it names." **Round ten falsified that too**, and
      more broadly. The round-nine repair removed three *discovery* variables from an
      inherited environment. That list is complete for its class — `GIT_COMMON_DIR`,
      `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE` and
      `GIT_CEILING_DIRECTORIES` were all checked and all leave a seeded victim intact —
      and it is the wrong class. Git **configuration** injection is strictly more
      powerful, because injected configuration is executed as a command: with no `GIT_*`
      variable set at all, a `HOME` whose `.gitconfig` names `core.fsmonitor` took three
      `IMMUTABLE_REVIEWED_PREFIXES` files out of another repository's index while the
      suite reported `OK` and the door passed. Two consecutive rounds stated a universal
      ("anything", "regardless of what it names") on the strength of a check that could
      only fail for the names its author had thought of.

    * Round ten built the chokepoint and then stated that its enumeration made a
      twenty-fourth call site fail the suite. **Round eleven falsified the enumeration,
      not the chokepoint.** `_spawn_sites` matched `ast.unparse(node.func)` against 19
      literal dotted spellings, so `from subprocess import run as _spawn` and a call
      inside `_reviewed_manifest_digest` took all three `IMMUTABLE_REVIEWED_PREFIXES`
      families out of a victim repository's index with the suite reporting `Ran 244 … OK`
      and the enumeration reporting `offenders: []`. The environment construction held —
      the bypass had to widen the environment itself to do damage — but the *structure*
      claim did not. Three rounds running, a universal was stated on the strength of a
      list of names its author had thought of, one level up each time: Git command names,
      then environment variable names, then Python API spellings. §11.17.3 has the
      reproduction and the repair.

    **What is true now, stated as narrowly as the evidence supports.** Every Git
    subprocess this module spawns — reading or writing, 23 call sites reduced to one —
    goes through `_git`, and every documented shell block through `_run_shell`. Both
    build their environment with `_allowlisted_env`, which **constructs** it from ten
    named variables and never reads `os.environ`. So the claim is no longer "these
    hostile names are removed" but "nothing the caller set is present", which holds for
    names nobody has invented yet; `GitSpawnChokepointTests` asserts it over the whole
    mapping, values included, and `GitSpawnChokepointTests.test_every_process_this_module_spawns_goes_through_a_chokepoint`
    parses this module's own source, resolving import bindings and enclosing scopes, so a
    twenty-fourth call site fails the suite instead of inheriting a convention — under any
    import spelling and at any nesting depth, with the exception recorded as item 17.
    §11.16 has the chokepoint's reproduction, repair and mutations; §11.17.3 has the
    enumeration's.

    **What is still outside it, and is not asserted away:**
    - **Anything with write access to the trusted `PATH` directories.** `git` is
      resolved to an absolute path found only on `TRUSTED_PATH`
      (`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`), and that same
      `PATH` is what Git itself is given, so hooks, `git-` subcommands, filters and
      `core.fsmonitor` are resolved there too. An attacker who can write into those
      directories has already won the host, and no test module outranks that. It is a
      recorded limitation, not a closed one.
    - **The repository's own local configuration.** `.git/config` and `.git/hooks` of a
      repository this module operates on are that repository's, not the caller's. For
      `REPOSITORY_ROOT` that is the tree under review and is in scope by definition; for
      `_CheckpointSandbox` it is a copy of the same. The allowlist neutralises the
      *ambient* channel — system, global, `GIT_CONFIG_*` — and says nothing about local
      config, deliberately.
    - **Other modules in the same test run.** This is a live finding, not a hypothetical:
      see §11.16.6. `scripts/validate_bootstrap.py` and
      `tests/contract/test_validate_bootstrap.py` spawn Git with an inherited
      environment, and both are forbidden hotspots for this task.
    - The forbidden-hotspot proof is unaffected and is still made the same way — `git
      status` on this repository after the whole suite has run.
16. **`_retro_edited_digests` examines at most 60 manifest revisions.** A retro-edit
    older than that is not looked at. This is bounded coverage, not a wrong answer, which
    is why it was left alone when the `_freeze_commit` window was removed for producing
    one — see §11.13.5. It is recorded here so the two are not read as one fix.
17. **What a source-level enumeration cannot see, and what a pin cannot promise.** Two
    caps, both recorded rather than chased, because a check beside a claim it cannot make
    is the defect this module has spent four rounds removing.

    * **Dynamic dispatch.** `_spawn_sites` resolves import bindings, so a spawn is found
      whatever it is spelled and wherever it is nested. It cannot resolve a name that does
      not exist until the program runs: `eval`/`exec` over an assembled string,
      `importlib.import_module` with a computed name, `getattr(subprocess, <computed>)`, a
      callable passed in as an argument or read out of a dict, and rebinding an imported
      name at run time. Round twelve adds two more, and they are a different kind: a class
      defined in this file whose base is a spawning API and which is called by its own
      name, and an attribute reached through a call's return value such as
      `multiprocessing.get_context('fork').Process`. Both *are* spelled out statically;
      resolving them would take class-hierarchy analysis or return-type inference, neither
      of which this module does and neither of which it now claims.
      `UNRESOLVABLE_SPAWN_ROUTES` records the seven routes as data and `ALIAS_BYPASSES`
      carries four of them as rows whose expectation is deliberately empty, so their
      silence is a decision rather than an oversight. A third route the same reviewer
      named, `concurrent.futures.ProcessPoolExecutor`, was a genuine gap rather than a cap
      and is closed: it is an ordinary dotted name, it is in `SPAWN_APIS`, and
      `ALIAS_BYPASSES` carries it as a row that goes red if the entry is removed. **The claim the
      enumeration makes is that an honest edit is caught** — a new caller written the way
      the existing ones were fails the suite the moment it is written. It is not, and is
      not offered as, a control on an author with write access to this file who intends to
      run a subprocess. A test module does not outrank its own author.
    * **Table pins.** `TableExpectationTests` proves a literal expectation *exists* for
      every table in this module; the expectations themselves are what prove the contents,
      and they are written out one table at a time to be read against the definitions. The
      scan will not accept `assertIn`, a self-comparison or a projection, and the negative
      controls drive each of those. It will accept a cardinality pin, `assertEqual(len(T),
      n)`, which turns emptying and shrinking red and says nothing about the values — used
      for `WritingCommandGuardTests.CASES`, whose rows hold lambdas that no literal
      restates, and for the two probe tables whose rows carry their own expectations.
      Where the pin is on cardinality the report says so.
18. **Four constants whose *width* is unpinned, measured rather than asserted.** An
    independent reviewer reported that `ACCEPTANCE_EVIDENCE_PREFIX`,
    `RATIFIABLE_REVIEWED_PREFIX`, `POST_FREEZE_STRANGER` and `_ManifestHistory.PREFIX`
    "can each be rotated with 281 green" — further members of the class §11.16.8
    discloses four of. Rotated one at a time against the full suite, that is true of one
    of them and only partly true of two; the measurements are in §11.18.5 and the
    corrected statement is that **the guarantees are not vacuous, their widths are
    unpinned in the widening direction**. `ACCEPTANCE_EVIDENCE_PREFIX` widened to
    `artifacts/` or `artifacts/checkpoints/` leaves 281 green, and moved out of
    `artifacts/` altogether turns 38 tests red; removing the check outright is caught by
    `test_a_report_path_outside_the_evidence_prefix_licenses_nothing`, which self-adapts
    to whatever the prefix is and therefore cannot see a widening. That is the exact
    shape of the limitation: what is guaranteed is that report paths are confined to
    *some* declared prefix, not that the prefix is the narrow one. The remedy is a
    literal pin, which is what §11.17.1 did for tables; it is recorded rather than made
    because this is the last round of this task and a pin added without an independent
    review is a change nobody checked.
19. **The table census sees tables by four syntactic shapes.** `_module_tables` finds an
    `UPPER_CASE` name bound, at module or class level, to a container display, a
    `frozenset`/`set`/`tuple`/`list`/`dict` call, or a union of those. A table built by a
    comprehension, bound by chained assignment, returned from any other call, or given a
    lowercase name is invisible to it, and `TableExpectationTests` would report no
    finding about it. **None exists today**: scanned with a deliberately wider predicate,
    the module has zero such bindings, and every `UPPER_CASE` name the census does not
    see — 38 of them — is a scalar rather than a table. Recorded so the census reads as
    "every table in the four covered shapes" rather than "every table".

### 11.2 The policy, stated once so it cannot be widened by reading

**`contracts/**`, `fixtures/**`, `scripts/**` — never.** Ratification does not reach
them. No record can license a byte. `test_the_three_untouchable_families_are_byte_identical`
asserts this on its own, independently of the ceiling below, so the guarantee does not
depend on reading the ceiling correctly.

**`docs/architecture/**` — only when all of these hold at once:**

1. an external record exists at `artifacts/checkpoints/CP-00/manifest.json` — outside
   every reviewed family, because a record living inside the tree it authorises could
   license its own drift — and it says `"ratified": true`;
2. that record carries a `ratification` object naming `allowed_delta_paths` explicitly,
   as a non-empty list of unique repository-relative paths;
3. it also carries `task`, `decided_on`, `decided_by` and `reason`, all non-empty
   strings, and `task` is `W0-INT-01` — the only task the wave plan authorises to
   ratify. A delta authorised by a bare boolean would be an accident with a flag on it;
4. every named path lies under `docs/architecture/`, lies inside the ceiling in §11.3,
   and **already existed at `reviewed_candidate_commit`**. A path that did not exist at
   the candidate is a *new* reviewed artifact: that needs review, not ratification.

Anything else under `docs/architecture/**` is drift and fails, exactly as before. A
record that violates any condition is **inadmissible and licenses nothing at all** — not
even the paths it names that would have been fine — so a half-correct record cannot
smuggle a delta through.

5. and the observed delta must **equal** the declared one. Not "contain", not "be
   contained in": every declared path must actually differ from the candidate, and no
   other reviewed path may. Round four added this direction; without it a record could
   declare all five reconciliations, perform one, and pass (§11.8).

Drift is still *observed and reported* under a valid record; it is licensed, not
invisible. `test_declared_ratification_of_the_whole_ceiling_is_accepted` asserts both
halves: `_undeclared_drift` is empty and `_drifted_reviewed_paths` still returns all
five paths.

### 11.3 The ceiling, and why the record cannot widen itself

A record that could name any path would be no control at all: the integrator writes the
record, so it could authorise whatever it had just changed. So the module pins a closed
ceiling. **The record must name exactly the ceiling: never a path outside it, and — from
round four — never fewer either.** Naming fewer was the false positive §11.8 records; for
CP-00 each of the five is a reconciliation ratification owes, not an option.

```text
docs/architecture/ADR_INDEX.md
docs/architecture/ARCHITECTURE_LINT_RULES.md
docs/architecture/CP00_ARCHITECTURE_REVIEW.json
docs/architecture/CP00_ARCHITECTURE_REVIEW.md
docs/architecture/CP00_OWNER_DECISIONS.md
```

Those five are exactly the artifacts CP-00 ratification is recorded as needing: the
review document whose `ratified` flag *is* the ratification act, in both its forms, plus
the three point-in-time statements the checkpoint manifest lists under
`known_pre_ratification_items` — the `PD-02` precondition text in two documents, the
stale `GATE-E` prose in the lint specification, and the owner-decision count in the ADR
index. They are also exactly the `docs/architecture/` entries in `W0-INT-01`'s allowed
paths. Nothing else in that family is reconciled by ratification.

The ceiling lives in `tests/contract/test_cp00_candidate.py`, which only `W0-QA-01`
owns. **Widening it means editing this module, which means reopening this task and
passing another independent review.** That is the whole anti-widening argument: the
record can neither grow the delta nor shrink it, and the thing that could grow it is not
writable by the task that would benefit.

### 11.4 The flag is compared, not pinned

`CP00_ARCHITECTURE_REVIEW.json`'s `ratified` must equal the external record's
`ratified`, in **both** directions:

- review `true`, record absent, `false` or inadmissible → **fail**. This is the original
  danger, unchanged: a candidate cannot ratify itself.
- record `true`, review still `false` → **fail**. A recorded ratification the artifact
  does not carry is equally a contradiction, and the old pin could not see it.

Three further consistency checks tie the external record to reality, so it cannot be a
convenient fiction:

- **`CHECKPOINT_REGISTRY.md`'s CP-00 row and the manifest may not contradict each
  other**, compared by structure — see §11.7, which replaces the prose predicate an
  independent review rejected;
- the manifest may not contradict itself: `ratified: false` with a `ratification` object
  present is refused, so a record cannot pre-authorise a delta it has not taken;
- the manifest's `artifact_manifest_sha256` and `artifact_count` must match the tracked
  reviewed families, and `candidate_digest` with `candidate_file_count` must match the
  tree the digest describes — both recomputed with the manifest's own recipes. Before
  ratification the first is the candidate digest; after ratification the integrator must
  recompute it. A record that kept the pre-ratification digest would be describing a
  tree that no longer exists.

### 11.7 Round three — the registry comparison, rebuilt on structure

An independent review returned **REJECT** on one defect, and it was in the class this

**The defect.** `test_the_two_external_records_do_not_contradict_each_other` asked
whether the CP-00 registry row contained the word `ratified`, via `\bratified\b`. That
pattern matches inside **`not ratified`**, so a row *denying* ratification was
indistinguishable from one confirming it. The miss was two-sided, and the reviewer
produced both halves:

| Registry row | Manifest | Old verdict | Correct verdict |
|---|---|---|---|
| `ratified 2026-09-02; tag not yet published` | `ratified: true` | pass | pass |

| `not ratified; not tagged` | `ratified: false` | **fail** — the honest state refused | pass |

The middle row is the live one. §11.5 tells `W0-INT-01` that its next action is to edit
exactly that registry row, and the only gate supervising that edit accepted a row
denying the ratification it was supposed to confirm. The bottom row is worse in a
quieter way: the check refused today's honest state with a message asserting the
opposite of the file it had just read. My round-two probe #11 exercised only the
*stale* wording `ratification blocked`, which happens to be caught. The negation case
was never tried.

**The repair, and what it is not.** It is not a better regular expression. The row is no
longer read as English at all. What is read is the one machine-readable element the row
already carries: it cites, in a code span, the state key from a **closed two-value
vocabulary** — `` `ratification_blocked` `` while blocked, `` `ratification` `` once
ratified. These are identifiers, not words; no sentence around them can negate them,
because no sentence is consulted. The rule is then a single comparison: the row cites
exactly one token, and `token == "ratification"` must equal the manifest's `ratified`.

Two things this deliberately does **not** do. It does not require the manifest to still
carry a key of that name — an unratified manifest has no `ratification` object and a
ratified one may retire `ratification_blocked` as spent history, so tying the comparison
to key presence would couple it to whether history was kept. That coupling was in my
first attempt at the repair and it failed on the ratified tree; it is now removed and
pinned against by `test_the_comparison_does_not_depend_on_manifest_history`. And it does
not invent a registry column: it formalises a convention the row already follows, and it
is satisfied by the registry exactly as it stands today, so nothing is red while the
decision is pending.

**A format request, not a smuggled format change.** The registry's Status column is free
prose and carries no state field. This module now reads a token inside that prose rather
than the prose itself, which is enough and costs `W0-INT-01` a one-token edit. If the
repository owner would rather the registry carry a **first-class machine-readable state
column** for every checkpoint — the cleaner answer, and one this task cannot write — that
is a registry-format decision for the checkpoint-registry owner. Recorded here as a

### 11.8 Round four — declaring the work is not doing it

An independent negative probe found a **false positive**: the green suite could confirm
a ratification that was declared and not performed. The reviewer declared all five
files, changed **one**, and got `problems: []`, `undeclared: []`, `95/95 OK`. Four
obligatory reconciliations skippable, with the record still claiming them.

**Why it was there, and it was pinned deliberately.** `_undeclared_drift` computed
`observed − declared`: it asked only what changed without being declared. The other
direction — what was declared and never changed — was not computed at all. Worse, a test
of mine, `test_a_partial_declared_ratification_is_accepted`, asserted that "the record
may name fewer paths than the ceiling", which fixed the hole in place as a property. The
ceiling protects against the integrator declaring **more** than allowed; nothing
protected against declaring the full set and doing none of it. For CP-00 those five
files are not a menu — they are the flag, the `PD-02` precondition in two documents, the
stale `GATE-E` sentence and the `ADR_INDEX` decision count.

**The repair.**

- The declared set must now equal the ceiling **exactly**. A record naming fewer paths
  is inadmissible and licenses nothing, under the same one-violation-voids-the-record
  rule that already governed naming too many.
- The delta is compared for **equality**, not inclusion: `observed == declared`. The new
  `_unperformed_declarations` computes `declared − observed`, and
  `_ratification_delta_problems` reports both directions plus the immutable families in
  one answer.
- `test_a_partial_declared_ratification_is_accepted` is **inverted** into
  `test_a_partial_declaration_is_rejected`, carrying a note saying what it used to
  assert and why that was wrong.
- The probe that used to check "a file outside the declared set is still drift" had
  become a duplicate once the declared set was forced to the whole ceiling; it is
  repurposed into `test_both_directions_are_reported_at_once`, which skips one
  reconciliation *and* edits a stranger in the same tree and requires both to be named
  from a single evaluation, so neither failure mode can mask the other.

**Both directions, end to end on a real ratified tree.**

| Scenario | Required | Observed |
|---|---|---|
| declared 5, performed 5 | pass | **ACCEPTED**, 98/98 |
| declared 5, performed 1 — the reviewer's false positive | fail | **REJECTED** |
| declared 2, performed 2 | fail | **REJECTED**, record inadmissible |

The rejection names the work that was not done:

Two in-suite probes pin the same thing in the normalised sandbox:
`test_declaring_five_reconciliations_and_making_one_is_rejected` reproduces the

`test_a_fully_declared_and_fully_performed_ratification_is_accepted` holds the other

One thing this does **not** do: `test_the_reviewed_families_carry_nothing_undeclared`,

### 11.9 The acceptance digest split — request made, request met

The program integrator replaced `candidate_digest` with `tested_candidate_digest` and

**All three are now closed, by the integrator, in the manifest:**

### 11.11 Round six — a guarantee the arithmetic did not provide

The fourth layer of the same defect, and the root of this one was in the manifest recipe
rather than in my code — but the false claim was mine, in a docstring and in §11.9.

**What was claimed.** That recomputing `evidence_bundle_digest` binds the evidence to
the tree the acceptance streams judged, "so evidence from a different tree cannot be
presented as this round's".

**What the arithmetic did.** The recipe blanked **both** acceptance digest fields, so
the evidence digest was mathematically independent of `tested_candidate_digest`. An
independent reviewer built two honest, complete ratifications differing in that value
alone — including `deadbeef…`, describing a tree that never existed — and got one
identical evidence digest and a green suite from both. I reproduced it:

| `tested_candidate_digest` | blank **both** (old recipe) | blank **computed only** (corrected) |
|---|---|---|
| `aaaaaaaaaaaaaaaa…` | `f219e199e12f6a8d` | `2914d6d2130d3e6e` |
| `0000000000000000…` | `f219e199e12f6a8d` | `306b3c18886929b1` |
| `9f9f9f9f9f9f9f9f…` | `f219e199e12f6a8d` | `05b7a6cfaaadb833` |

One column is a constant. The field naming which tree was judged could hold any 64-hex

**Why this is the same class, one layer down.** The wave has rejected candidates three
times for a gate whose claim lived in prose rather than in checkable structure. Here the
gate existed, ran, and passed — but it could not fail on the thing the prose beside it

**The repair.** `_acceptance_digest` now takes the field being computed and blanks that
one alone, at the top level and in every `acceptance_rounds` entry, matching the
corrected recipe. The binding claim is removed from the docstring and from §11.9 and
replaced by two probes:

- `test_the_evidence_digest_depends_on_the_tested_digest` — three trees identical except
  for that value must produce three different evidence digests;
- `test_swapping_the_tested_digest_alone_breaks_the_evidence_digest` — substituting
  `deadbeef…` into an otherwise valid ratification must be rejected by the live check.

**Three secondary points, all taken, all the same principle.** A requirement that the
candidate already satisfies cannot distinguish work done from work skipped:

- `must_contain: ("GATE-E",)` was doing duty as reconciliation evidence while `GATE-E`
  is already in the document three times. Positive requirements are now split:
  `new_text` must be **absent at the reviewed candidate**, and the lint entry is marked
  `removal_only` with a `must_still_contain` guard that no longer pretends to be
  evidence. An entry with neither a positive requirement nor `removal_only` is itself
  reported as a defect.
- The `62`/`31`/`satisfied` sentence conjunction gets the same guard: it must not be
  satisfiable at the candidate.
- `review_status` must be a token **not already present** in the candidate's Markdown,
  or requiring the Markdown to quote it proves nothing.
- `_retro_edited_digests` is silent against the repository. The comparison is extracted
  into `_digest_history_problems` and proved on synthetic history:
  retro-edit, entry deletion and renumbering are each caught, and opening a new round
  correctly stays silent.

  **Corrected in round eight.** This bullet used to explain the silence by saying "every
  committed manifest so far carries `""` in every per-round digest, because no round has
  yet been sealed". That is false. `5207fb5` seals round 5 with
  `22e3027b2721d60810ed088911c4cf3ebcfe86a50f6a1fa9e606c2da91177c3a`, and it is the only
  one of the manifest's ten commits carrying a per-round value at all; the other nine
  carry `""`. The check is silent because that value has not *changed* between commits —
  which is the thing it looks for — not because there is nothing to compare. The
  distinction is the whole point: "nothing to compare" would mean the rule is untested
  here, and "one value, unchanged" means it is running and satisfied. Round eight's
  reviewer made it fire on real commits with a set/changed/set-back history.

**Both directions, re-run end to end after the change:** a full content-correct
ratification is **ACCEPTED** at 140/140; the byte-only reconciliation and the unaccepted
round are still **REJECTED** by their own checks.

### 11.12 Round seven — a digest nobody recomputed, a guard that could not fire, and a document caught between two guarantees

Three findings. The first two are the same defect class one more layer down: a check that
runs, passes, and cannot fail on the thing named beside it. The third is not a defect in
anything already written — it is a collision between two correct guarantees that the
program integrator found while preparing `W0-INT-01`, and it had to be resolved here
because the module that creates it is this task's.

#### 11.12.1 `tested_candidate_digest` named a tree nobody checked existed

**What was claimed** — §8.12 and the module docstrings, in every earlier round: that the
tree the value describes "stops existing the moment the results are written into it, so
it cannot be recomputed after the fact by anyone", and that because the recomputed
`evidence_bundle_digest` depends on it, "a value naming a tree that never existed cannot
sit there unnoticed".

**What an independent reviewer did with that** — built a complete, content-correct
ratification: five reconciliations actually made, both streams `PASS`, both primary
reports on disk, the registry row moved, the review's two halves in agreement — and set
`tested_candidate_digest` to `deadbeef…`, sealed **in the order the manifest's own recipe
prescribes**. Every check stayed silent and 140 tests passed. Dependence made the two
digests move together; it never asked whether the tested value named a real tree.

**Why the premise was false.** The recipe blanks only the field being computed, so the
value is exactly the digest of the tree at the commit that froze it — and Git keeps that
tree forever. The manifest never has to record its own hash: history supplies it. The
freeze commit is discoverable as the *oldest consecutive* commit of the manifest carrying
today's value both at the top level and in today's `current_round` entry, so a value that
was set, changed and set back resolves to the commit that froze the value now in force
rather than to an older coincidence.

**The repair, in two halves that are not interchangeable.**

- `_tested_digest_problems` — the value must be frozen at a commit and must reproduce as
  the digest of *that commit's tree*. A fabricated value fails twice over: it is frozen at
  no commit at all, and a manufactured one would not reproduce. Deliberately outside the
  ratification gate: a frozen digest is a claim about the world from the moment it is
  written, not from the moment somebody ratifies on it.
- `_post_freeze_delta_problems` — half one stays green however far the working tree drifts
  afterwards, because the freeze commit is immutable. So at ratification the delta between
  the frozen tree and the tree in front of you must lie inside `POST_FREEZE_DELTA_CEILING`
  plus the round's own declared acceptance evidence, honoured only under
  `ACCEPTANCE_EVIDENCE_PREFIX` so that a round cannot license its own drift by naming the
  drifted file as its report.

The recipe is expressed once, over an abstract `(paths, read)` pair, because it must run
over the working tree and over a commit's tree and those must not become two
implementations that can drift apart.

#### 11.12.2 The `must_still_contain` guard could not fire

The enforcement of `must_still_contain` read `if False and needle not in current` — an
unreachable branch. The `stale GATE-E probe prose` entry is `removal_only`, so that guard
was its **only** remaining protection: the removal could have been satisfied by deleting
the entire `GATE-E` probe description, destroying the thing being reconciled. This is
precisely the defect class the module exists to catch, found inside the module itself,
and it is the reason §8.13's claim that "each removal is paired with a positive
requirement" had to be corrected as well — it was never true of the removal-only entry,
by design.

Shown failing before and passing after, on the same probe. The old form is reconstructed
in memory from the module's own source and executed with the real `__file__`, so only
that one line differs and nothing on disk changes; the driver lives in a temporary
directory because this task may add no file to the repository.

$ .venv/bootstrap/bin/python "$TMP/probe_before_after.py"

[BEFORE: if False and needle not in current] guard fires: False

#### 11.12.3 The state document was caught between two guarantees

Found by the program integrator, not by me, and it is a deadlock rather than a
strictness. `_digest_paths` enumerates tracked-plus-untracked-not-ignored over the whole
repository, so `docs/program/CURRENT_STATE.md` is inside the digest. It was not in
`POST_FREEZE_DELTA_CEILING`. And it says, in as many words, `Nothing is ratified, nothing
is tagged` — a sentence that must go when CP-00 is ratified, or a ratified checkpoint
ships a state document denying its own ratification.

So ratification had two horns and no third option, both reproduced on the live checks:

| module | at ratification | `_acceptance_problems` | state document still denies |
|---|---|---|---|
| round six | state document **updated** | `round 5 is void: … nothing licenses them: ['docs/program/CURRENT_STATE.md']` | no |
| round six | state document **left alone** | *(empty — accepted)* | **yes** |
| round seven | state document **left alone** | `docs/program/CURRENT_STATE.md still says 'Nothing is ratified, nothing is tagged' while artifacts/checkpoints/CP-00/manifest.json declares ratified=true` | yes |

**Confirming what the integrator could not settle by reading:** before this round nothing
anywhere checked `CURRENT_STATE.md` against the manifest. `_registry_state_problem` covers
the checkpoint registry; the state document appeared in the module exactly twice, both
times as the *stranger* in a post-freeze probe. The second horn was entirely unguarded.

**The resolution, and what it costs.** `docs/program/CURRENT_STATE.md` is licensed as the
**third external record**, alongside the manifest and the registry. That is not a
convenience: all three are program-level records that must move *at the ratification act
itself*, after any possible freeze, because none of them can truthfully say CP-00 is
ratified before CP-00 is ratified. The registry is licensed for exactly that reason and
this document is in the same position.

Licensing alone would have been a widening with nothing bought back, so
`_state_document_problems` is what the licence pays for, and it is checked in **both**
directions:

- `ratified: false` — the denial must be **present**. This is the anti-vacuity half, and
  it is why this is not modelled as a `RECONCILIATIONS` entry (see below). Reword the
  sentence and the check fails *now*, loudly, while CP-00 is still unratified and
  re-anchoring costs nothing.
- `ratified: true` — the denial must be **gone**, and `STATE_DOCUMENT_MUST_STILL_CONTAIN`
  must survive, so the removal cannot be satisfied by deleting the document. That guard
  is the `GATE-E` lesson of §11.12.2 applied immediately: it is a guard, not evidence.

**Why not a `RECONCILIATIONS` entry, which is what the integrator suggested first.**
Every entry in that table anchors its stale phrase to the file **at the reviewed
candidate**, and the state document is not a reviewed artifact — the program rewrites it
every round, outside review. The ratification-relevant sentence has already been
rewritten twice since `reviewed_candidate_commit`:

```text
92e13fa (reviewed candidate): "Nothing is frozen, nothing is ratified, and production
                               implementation remains locked."
5207fb5 (today / freeze):     "Nothing is ratified, nothing is tagged, and production
                               implementation remains locked until CP-01."
```

`nothing is ratified` is present at the candidate and absent today; `Nothing is ratified`
is absent at the candidate and present today. A candidate-anchored entry would therefore
have reported anchor rot the moment the integrator wrote an ordinary state update, and
the only fragment present in both — `is ratified` — is one a *ratified* state document
will obviously still contain, so requiring its removal would be wrong in the opposite
direction. The live document, checked in both directions, is the anchor that holds for a
living document.

**The integrator's second option was declined, and why.** Closing the post-freeze window
at ratification would make the check go quiet at the exact moment the tree is published —
the shape of a guard that cannot fail, which is the defect this round found twice
already. Nothing about the window is closed; only one path is licensed inside it, and the
licence is answerable to a check.

**The probes' stranger had to move, and the replacement is chosen for a property, not for
readability.** `docs/program/CURRENT_STATE.md` was the canonical unlicensed path in two
post-freeze probes; licensing it would have left those probes asserting that a licensed
file is unlicensed. `POST_FREEZE_STRANGER` is now `contracts/README.md`, and the probes
assert the property rather than trusting it: it starts with one of
`IMMUTABLE_REVIEWED_PREFIXES`, whose stated policy is that ratification does not reach
them and no record licenses a byte, it is not in the ceiling, and it is not under
`ACCEPTANCE_EVIDENCE_PREFIX`. Licensing it would mean abandoning a policy, not extending
a list.

#### 11.13.2 BLOCKING — "oldest consecutive" was asserted, claimed twice, and untested

`_freeze_commit`'s docstring, §11.12.1 and §8.12 all say the walk takes the *oldest
consecutive* commit carrying the value. Replacing `freeze = commit` with `return commit`
— "the newest commit carrying the value" — left all 159 tests green. It was the only
survivor of the reviewer's seventeen mutations.

**The property is load-bearing.** On the honest sequence the streams' results are
recorded into the manifest after the freeze, so freeze `F` and results `G` both carry the
value while only `F`'s tree digests to it. A newest-first implementation returns `G`, and
the declared digest stops reproducing — which is the whole of half one.

**The degeneracy that hid it** is the one §11.11's third point claims to have removed. In
every probe the two implementations coincide: the live repository froze at `HEAD` and has
recorded no results since, and the sandboxes copy a tree and never commit.
`test_the_tested_digest_recomputes_over_the_commit_that_froze_it` is satisfied by any
implementation correct at `HEAD`, and
`test_a_tested_digest_that_does_not_reproduce_at_its_freeze_commit_is_rejected` mocks
`_freeze_commit` away entirely.

It is worth being exact about how deep that goes: **even the published clone of §11.13.1
does not discriminate.** Its `HEAD` is two commits past the freeze, but neither touches
the manifest, so `git log -- manifest` still lists the freeze commit first and both

mutant (newest carrier)        freeze=5207fb557292  is HEAD? False

the integrator records a verdict.

#### 11.13.3 The retired `-n 200` window, and the choice you asked me to make

The reviewer reported that with 216 manifest revisions carrying the value the old walk

unsafe direction — and the two probes for it are careful to fail the third `show` rather
than the first, because with every revision unreadable both implementations return `None`
and the probe would prove nothing.

#### 11.15.1 BLOCKING — the writing guard validated the path and not the destination

> **Correction, round ten.** This subsection's finding and repair stand and are kept as
> the record of round nine. Its closing claim does not: the environment *could* still
> redirect a write, through Git configuration injection rather than through repository
> discovery, and the repair reached 5 of this module's 23 Git call sites rather than all
> of them. §11.16.1 has the reproduction; §8 item 15 states what is true now. Read the
> paragraphs below as round nine's account, not as the current guarantee.

`_CheckpointSandbox._git_write` and `_ManifestHistory._run` both call
`_refuse_to_write_outside(...)` and then run `git -C <root> ...` with no `env=`. `-C` sets
only the working directory Git starts repository discovery from. `GIT_DIR`,
`GIT_WORK_TREE` and `GIT_INDEX_FILE` override discovery outright and are not overridden by
it, and neither call sanitised them. Reproduced against the bytes on disk, with a
legitimate `mkdtemp` sandbox root — the guard's path check passing cleanly — and a
throwaway victim clone:

```text
victim clone tracked before: 1
victim clone tracked after:  0        # BEFORE this round's fix
victim byte-identical:       False
_git_write raised:           None     # the guard did not fire
```

A file from `IMMUTABLE_REVIEWED_PREFIXES` was dropped from another repository's index
while the guard reported nothing wrong. The module already treats `GIT_DIR` as a live
hazard in this repository — the comment now at §3.1 of this report and `_run_shell`'s
`env.pop("GIT_DIR", None)`, both pre-dating this round — but that fix reached only the
read-only helper, not the two writers.

**The repair.** A shared `_sanitised_git_env()` returns `os.environ` with `GIT_DIR`,
`GIT_WORK_TREE` and `GIT_INDEX_FILE` removed, and both writers now pass it as `env=`.
`_run_shell` is rebuilt on the same helper rather than its own narrower `GIT_DIR`-only
pop, so the read path and the two write paths are one sanitisation, not three. Re-run
after the fix, same victim, same hostile triple:

```text
victim clone tracked before: 1
victim clone tracked after:  1        # AFTER this round's fix
victim byte-identical:       True
```

**The guard alone was never going to be enough, and that is the general lesson, not a
one-off.** A guard that validates the path argument proves a fact about the argument; it
proves nothing about where the command actually reaches, because Git's own repository
discovery admits inputs the argument list does not mention. Only measuring the
destination — before and after, on a real victim — establishes the property. This is the
same shape every round of this task has been reopened for, one layer further down: a
guarantee stated in prose (the guard's own docstring said "nothing writes to the
repository under review") beside a check that could not fail on the thing the prose
named, because the check only ever looked at the one input it had been handed.

**Proof, in the suite.**
`WritingCommandGuardTests.test_a_hostile_git_dir_cannot_redirect_either_writer` builds a
throwaway victim repository (never `REPOSITORY_ROOT`), points both writers at it through
`GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` set on the test process's own environment —
exactly how a post-commit hook, `git rebase` or `git bisect run` would set it — and
asserts the victim's tracked-file listing and file bytes are unchanged, while also
asserting each writer's *intended* target did receive the write, so the probe cannot pass
by both commands silently failing.
`test_removing_the_environment_sanitiser_lets_the_hostile_git_dir_through` reconstructs
the pre-fix call verbatim — the same two lines, with `env=` deleted — from the module's
own source, executes it against the same construction, and requires the victim's tracked
set to move; a run that leaves the victim untouched would mean the reconstruction is not
faithful, and the probe fails on that basis rather than passing vacuously. Together the
two tests are the before/after the standing rules require, held inside one suite rather
than as a one-off script: against the **pre-fix call** (no `env=`), the victim's tracked
files move, which is what `test_removing_the_environment_sanitiser_lets_the_hostile_git_dir_through`
requires in order to pass; against the **current code**,
`test_a_hostile_git_dir_cannot_redirect_either_writer` requires the same victim to stay
byte-identical. Both are green today. A future accidental re-introduction of the missing
`env=` would be caught twice — the primary test would go red, and the reconstruction
test's own premise (that its hand-built old call is *not* how the module behaves) would
quietly become false in a way `test_both_callers_share_one_guard`-style source
inspection would not catch, since the reconstruction test does not read the real
`_git_write` at all; it is a deliberate, separate demonstration, not a substitute for
the primary regression test.

### 11.16 Round ten — a denylist for the wrong class, and a chokepoint that did not exist

Round nine repaired a real defect and stated a universal about it. Round ten's

The shape of the round-nine defect is worth stating before the details, because it is
the third time this task has produced it: **a guarantee written in prose beside a check
that cannot fail on the thing the prose names.** Round eight said "nothing writes to the
repository under review". Round nine said the destination "is not determined by anything

#### 11.16.1 BLOCKING F1 — Git configuration injection, a class the denylist did not name

`GIT_DISCOVERY_ENV_VARS = ("GIT_DIR", "GIT_WORK_TREE", "GIT_INDEX_FILE")` is **complete
for the discovery class.** The reviewer verified that directly: `GIT_COMMON_DIR`,
`GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_NAMESPACE` and
`GIT_CEILING_DIRECTORIES` all leave a seeded victim intact. Nothing about round nine's
list was wrong. It was a list, and the attack was not in it.

The class it misses is **Git configuration injection**, and it is strictly more powerful
than discovery redirection, because an injected configuration value is *executed as a
command*. With no `GIT_*` variable set anywhere — only a `HOME` whose `.gitconfig` names
`core.fsmonitor`:

```text
suite result : OK  (exit 0)
victim tracked: 3 -> 0
```

The three files that left that repository's index were `contracts/README.md`,
`fixtures/f.json` and `scripts/s.py` — all three `IMMUTABLE_REVIEWED_PREFIXES` families.
Pointed at a disposable stand-in for the repository under review: 214 tracked files to
147, immutable-family files 67 to 0. `_refuse_to_write_outside` passed cleanly on every
call and all 189 tests stayed green throughout.

Confirmed members of the class, each reaching arbitrary command execution:

| Channel | Reaches | Notes |
|---|---|---|
| `HOME` / `XDG_CONFIG_HOME` → `.gitconfig` | `core.fsmonitor`, `core.hooksPath`, `core.attributesFile` + `filter.*.clean` | no `GIT_*` variable involved at all |
| `GIT_CONFIG_PARAMETERS` | the same | what `git -c K=V` propagates to every child |
| `GIT_CONFIG_COUNT` + `GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` | the same | the structured form of the above |
| `GIT_CONFIG_GLOBAL` / `GIT_CONFIG_SYSTEM` | the same | names the file outright; an empty `HOME` does not stop it |
| `$PATH` shadowing of `git` | everything | 28 module invocations routed through an attacker binary, suite reporting `OK` |
| `core.excludesFile` (via any of the above) | no code execution, a **wrong answer** | changes what `--exclude-standard` enumerates, so `_digest_paths` under-reports and the module certifies agreement it never checked |

**This is inside the module's own stated threat model, not adjacent to it.** §11.15.1
names the motivating scenario as "a post-commit hook, `git rebase` or `git bisect run`".
What a post-commit hook's child actually inherits, measured:

```text
GIT_CONFIG_PARAMETERS='core.fsmonitor'='/tmp/evil.sh' 'user.email'='a@b' 'user.name'='a'
GIT_INDEX_FILE=.git/index
```

Round nine stripped `GIT_INDEX_FILE` from that line and left the other one. The same
benign invocation that motivated the repair delivers the vector the repair misses. And
`core.fsmonitor` is an ordinary setting real developers configure — under it,
`WritingCommandGuardTests` alone executed the ambient hook **16 times per run**,
including inside the test that asserts the victim is intact.

**The second half of the finding, and the one that mattered more.** The reviewer's AST
scan of the module found **23** `subprocess.run(["git", …])` calls, of which **5** passed
`env=` and **18** did not. Nine of the unsanitised were production helpers rather than
test bodies: `_candidate_reviewed_paths`, `_present_reviewed_paths`, `_candidate_blob`,
`_tree_blobs` (twice), `_digest_paths`, `_freeze_commit` (twice), `_retro_edited_digests`
(twice), `_reviewed_manifest_digest` and `_reset_to_the_frozen_tree`. Round nine's
`_sanitised_git_env` docstring said it was "shared by **every** Git subprocess this
module spawns, reading or writing … Neither is safe without this." It was shared by five
of twenty-three, and nothing anywhere measured the gap. The only thing keeping the other
eighteen in line was a convention, and `test_both_callers_share_one_guard` — which
counted the string `_refuse_to_write_outside(` inside two *known* writers — is a
spot-check of two, not a property of the file. A writer added later inherits neither the
guard nor the sanitiser, and no test notices.

#### 11.16.2 The repair — a chokepoint, an allowlist, and an enumeration that makes it structural

Three things, in the order they matter.

**1. One door.** `_git(...)` is now the only place this module spawns Git, and
`_run_shell(...)` the only place it spawns a shell. 23 call sites became 1. The
path-guard `_refuse_to_write_outside` is deliberately *not* folded into `_git`: it takes
a sandbox root and a prefix that a read has no notion of, and putting it there would mean
inventing a root for every `ls-tree`. The two checks are orthogonal and each has its own
enumeration.

**2. An allowlist, not a denylist.** `_allowlisted_env()` **constructs** the environment
and contains no reference to `os.environ` at all. Ten variables, each with its reason
recorded in `GIT_ENV_ALLOWLIST` and asserted to be recorded:

| Variable | Value | Why it is admitted |
|---|---|---|
| `PATH` | `TRUSTED_PATH` | `git`, `bash` and everything Git spawns must be findable; never the caller's |
| `HOME` | an empty `mkdtemp` directory | `~/.gitconfig`, `~/.config/git/config`, `~/.config/git/ignore` and `~/.git-credentials` are all reached through it, and an empty directory makes all of them absent at once. Unsetting it makes Git fall back to the passwd entry — the real home |
| `XDG_CONFIG_HOME` | an empty subdirectory | the second route to a global config and a global ignore file |
| `GIT_CONFIG_GLOBAL` | `os.devnull` | so the global config is empty by explicit statement and not only because `HOME` is — two independent reasons for one fact |
| `GIT_CONFIG_SYSTEM` | `os.devnull` | the same for `/etc/gitconfig` |
| `GIT_CONFIG_NOSYSTEM` | `1` | suppresses the system config on Git versions predating `GIT_CONFIG_SYSTEM` |
| `GIT_TERMINAL_PROMPT` | `0` | a suite that blocks on a credential prompt reports nothing |
| `LC_ALL`, `LANG` | `C.UTF-8` | the digest recipes sort paths and the documented gates read UTF-8 contract files; an inherited locale makes both answer differently on different hosts |
| `TZ` | `UTC` | any timestamp a documented gate prints is host-independent |

`GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_n`, `GIT_CONFIG_VALUE_n`,
every discovery variable and every name not in that table are absent **by construction**,
which is why the assertion can be stated over names that do not exist yet:
`test_a_variable_nobody_has_thought_of_does_not_reach_a_subprocess` invents one and
requires it absent, from the constructed mapping *and* from the environment of a real
child process.

There is exactly one deliberate widening, `env_extra`/`env_overrides`, and it is
enumerated rather than trusted: `DELIBERATE_ENV_WIDENINGS` names every call site that
uses it with its reason, and `test_every_deliberate_widening_is_named_and_justified_here`
fails on one that is not listed. Two of the eight are production —
`_MutableCopy.run_gate` and `DocumentedGateTests._assert_gate_passes`, both supplying
`GIT_DIR` because documented Gate C reads the repository's object database and a mutable
copy has none. The other six are negative probes that arm a vector before asserting it
is closed.

**3. The enumeration test, which is the part that turns a convention into a structure.**
`_spawn_sites` parses the module's own source and reports every call to any of nineteen
process-spawning APIs — not just `subprocess.run`, and not by looking for the string
`"git"`, because the failure mode being prevented is a *new* call site and a new call
site is exactly what a list of known command names misses. `_spawn_offenders` requires
every one of them to be a chokepoint whose `env=` is `_allowlisted_env(...)`. The current
count is **2 spawn sites, 0 offenders, 0 exemptions**: round nine's unsanitised
defect-reconstruction probe was the last one, and it is now narrowed to reconstruct the
property under demonstration through `env_extra` rather than by inheriting the caller's
whole environment. That probe was itself the entire residual leak from this module — see
§11.16.6.

Four probes make the enumeration falsifiable rather than decorative: a nineteenth caller
added to a synthetic source is reported by name and line; a chokepoint whose `env=`
becomes `dict(os.environ)` is reported; a chokepoint that passes no `env=` is reported;
and a helper nested inside a test body is attributed to *itself*, because attributing it
to the enclosing test would mean exempting the test, and exempting a test exempts
everything anyone later writes in it. A fifth,
`test_the_scan_is_reading_this_modules_real_source`, exists because every assertion above
is vacuously true over an empty string.

1. **Import bindings are resolved.** `_import_bindings` walks every `Import` and
   `ImportFrom` in the tree — function-body imports included, which is where somebody
   would put one — and `_resolved_target` rewrites a call's dotted spelling through them.
   `sp.run`, `run`, `_spawn` and `subprocess.run` are now one call. `SPAWN_APIS` becomes a
   list of APIs instead of a list of spellings.
2. **The missing families are added**, `l`-variants beside the `v`-variants, plus
   `pty.spawn`/`pty.fork`, `os.fork`/`os.forkpty`, the `asyncio` subprocess constructors
   and `multiprocessing.Process`/`Pool`. Thirty-seven entries, pinned literally.
3. **Chokepoint identity is a position, not a name.** `_scopes` reports a fully qualified
   scope, so a helper named `_git` nested in a test body is `T.test_x._git` and is not in
   `GIT_SPAWN_CHOKEPOINTS`. Round ten compared the innermost function *name*; the only
   thing that caught a counterfeit was the accident that the sorted list then held `_git`
   twice, which is a catch by side effect. `DELIBERATE_ENV_WIDENINGS` is keyed by
   qualified scope for the same reason: two classes may each hold an `_arm`, and a list
   keyed by simple name would let the second inherit the first's justification.
4. **`env=` is an equality on the call.** The predicate was
   `environment.startswith("_allowlisted_env(")`, which accepts
   `env=_allowlisted_env() | dict(os.environ)` — the allowlist and then the caller's whole
   environment merged over it. It is now "the `env=` value is a call whose resolved target
   is `_allowlisted_env`".

`_widening_sites` gained the three spellings it could not see: `**{"env_extra": hostile}`
read out of a dict display, an unreadable `**kw` into a chokepoint — reported, because a
scan that cannot read it must not conclude it is safe — and a direct
`_allowlisted_env({...})`, which is how a helper that had already borrowed a chokepoint's
name would widen without naming a keyword at all.

**The cap, stated rather than chased.** Dynamic dispatch no static analysis can resolve is
a **recorded limitation, not a defect**. `eval`/`exec` over an assembled string,
`importlib.import_module` with a computed name, `getattr(subprocess, <computed>)`, a
callable handed in as an argument, and rebinding an imported name at run time all reach
the same subprocess through a name that does not exist until the program runs. No list of
API spellings contains it and no AST resolves it. `UNRESOLVABLE_SPAWN_ROUTES` records the
five routes as data, `ALIAS_BYPASSES` carries `getattr` and `eval` as rows with an
*empty* expectation so their silence is deliberate rather than unnoticed, and
`test_dynamic_dispatch_is_a_recorded_limitation_and_says_so` holds each to a written
description.

So the claim this enumeration makes is bounded, and it is the claim worth making: **an
honest edit is caught.** A nineteenth caller written the way the eighteen were — under any
import spelling, at any nesting depth, on any of the thirty-seven API families — fails the
suite the moment it is written. An author with write access to this file who is determined
to run a subprocess can run one; a test module does not outrank its own author, and
pretending otherwise would put a check beside a claim it cannot make.
