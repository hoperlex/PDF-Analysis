## 1. Was the write half "an extension of `manifest.json` plus the walk"?

`W21-E2E` said so and `D-30` repeats it. The brief told me to verify it before relying on
it. **Measured: half right, and the wrong half is the one that would have mispriced the
work.**

**The manifest half is right, and it is the load-bearing half.** The write phase is a
`write` section of the same `manifest.json`, read by the same two checkers. No second
manifest, no second source of truth, no second npm script — and therefore **no
`web/package.json` change, no `package-lock.json` change, and no reason to go near
`web/FRONTEND_LOCK.json`**, which the brief flagged as a seal with `W22-WEB` live in it.
`e2e:pc01` already pointed at `journey.mjs`; the new phase runs under the same name.

**The "plus the walk" half is wrong.** The walk navigates and reads. Writing means pressing
the application's own controls, and `cdp.mjs` said in its own header that it *deliberately*
had no way to do that — "no selector engines, auto-waiting, actionability checks". So:

* `cdp.mjs` grew **five primitives** — `click`, `fill`, `attachFile`, `waitFor`, and a
  public `settle` — over **two more protocol domains**, `Input` and `DOM`. About 200 lines.
* The walk in `journey.mjs` **did not grow at all**. The write half is `write.mjs` beside
  it: same client, same manifest, same envelope, same exit code, 498 lines.

**What it actually takes,** stated for whoever writes the next `write` section (the upload
refusals are the obvious one): the primitives now exist, so that next section really *is*
manifest plus data. This one was not. Still no new repository dependency — `Input` and `DOM`
are two more documented CDP domains over the same built-in `WebSocket`.

## 3. How the wait is bounded, and what happens at the bound

The brief forbade sleeping, and a gated adapter was not available here either — so the
journey waits on **the application's own state**.

`web/src/widgets/run-progress/ui/run-progress.tsx` renders `data-run-outcome="in_flight"`
until `runOutcome` has a terminal to report, and `data-run-activity` alongside it. Those
readings are produced by `pollRunStatus`, the application's single run-progress loop, at
its frozen 2 s / ×1.5 / 15 s schedule. The journey polls the DOM attribute and does nothing
else: it starts no loop of its own, and it adds no cadence the seam document does not know
about.

**The bound is `await_terminal.bound_ms` in the manifest, currently 150 000 ms.** It lives
there rather than in the application because `polling.ts` says in its own header that the
app's loop deliberately has **no wall-clock deadline** — "inventing a timeout would invent
a failure the contract does not define". That reasoning is right for the product and wrong
for a test instrument, which must terminate.

**At the bound the journey reports a finding and exits 1.** Not a skip, not a pass, and not
a silent stop. Proven, not asserted — §4.

Two properties of the bound, stated because they are easy to misread:

* **It is a floor, not a stopwatch.** The condition is checked after each reading, so the
  measured wait is at least one poll. A 1 ms bound reports at ~503 ms, which is the first
  DOM read, not 1 ms.
* **Three falsy readings are kept apart**, because they are three different facts:
  `null` — the screen has not rendered an outcome yet; `false` — it has, and the run is
  still `in_flight`; anything else — a terminal. The envelope carries which.

Measured on the green run: **terminal `published` after 1 506 ms of a 150 000 ms bound**,
readings `0ms false` → `1506ms "published"`, and `data-run-activity="stopped"` afterwards
— which the journey also asserts, because a terminal run whose screen still claims to be
polling is a defect the state alone would not show.

## 5. Does the conformance guard cover it? Partly, and it was widened

**It did not, and the gap was exactly the one the brief predicted.** `W21-E2E` stated the
guard's cost as *"it checks addressing, not behaviour"*. The read walk is addressed
entirely by route and operation, so addressing covered all of it. The write half presses
named **controls** and reads named **markers** — `#new-project-name`, `#upload-file`, the
button labelled `Start run`, `data-created-project`, `data-run-outcome`,
`data-run-activity`. **None of those is addressing.** Rename an id in `web/src` and every
route and operation stays correct while the journey silently loses the ability to press
anything.

So the guard was widened. Seven new checks, twelve new controls, **11 → 30 tests**, still
inside `run_battery`, still with no browser, no origin, no port and no service:

1. the manifest has a write half at all, and it posts `startRun` (`D-30`, as a test);
2. every write step's `page_module` exists, derives to its own `at`, and that screen is one
   the read walk also covers;
3. **every handle the write half names still appears in `web/src`** — every `#id`, every
   `[data-*]` marker, every control label;
4. the uploaded fixture is on disk and non-empty;
5. every declared status is one the **contract** publishes for that operation — so
   `startRun`'s `202` is checked against `openapi.json`, not against taste, and a move back
   to a synchronous `201` reddens the gate;
6. every wait carries a **positive** `bound_ms`;
7. every run state named is one `RunState` publishes — `succeeded` is a stage status and
   naming it as a run terminal reddens.

The write half's operations also flow into the guard's existing contract check, so renaming
`startRun` — the operation `D-5` was — now reddens `make gate`.

**And the checks were proved against the real tree, not only against synthetic data.**
`tests/e2e/pc01/journey/prove_the_guard_can_fail.py` mutates the real `manifest.json` ten
ways, runs the matching check, and restores the file. Measured 2026-09-19, **ten mutations,
ten reds, zero vacuous checks**:

| drop the `write` section | ✓ |
| rename `startRun`'s operationId | ✓ |
| point `create-project` at a screen the read walk does not cover | ✓ |
| rename the project-name input's id | ✓ |
| relabel the `Start run` button | ✓ |
| drop the `data-run-outcome` marker | ✓ |

It is deliberately **not** a pytest file: it writes the tree ten times, and a thing that
writes the tree does not belong inside `make gate` where another lane may be measuring.

**What the guard still cannot see, stated plainly rather than left as a silent gap.**

* **An id existing in `web/src` is not the same as pressing it doing anything.** The guard
  proves the handle is there. Only the journey, against a running stack, proves the control
  works. The blind spot is narrowed, not shut.
* **The guard cannot see a 500.** `D-5` itself — the seam answering an error under a
  correct address, a correct operation and a correct handle — is invisible at gate time by
  construction, because the gate has no app to call. That check lives in the journey (*any
  `/bff/v1` call answering `>= 400` during a step is a finding, with its correlation id and
  body*) and nowhere else. **This is the residue, and it is the important one.**
* **Nothing makes a wave fail for not running the journey.** Unchanged from `W21-E2E`, and
  still the honest limit of the arrangement: what the gate guarantees is that the journey
  cannot silently stop *addressing* or stop *reaching* the product — not that anyone ran it.
* The coarse `web/src` scan is deliberately coarse. "This id is in this component" would
  encode where the programme keeps features today and go red on a file move that changed
  nothing a user sees.

## 6. Read the body, not the status — `D-28`, as checks

`/projects/<anything>` answers **200** and renders an error state, so no write step relies
on a status. Each one asserts, together: a declared status, a field of the **response
body**, a string the screen **rendered**, and the **absence** of the failure markers
`web/src` defines (`[data-upload-failure]`, `[data-precheck-problem]`, `[data-run-failure]`,
`[role="alert"]`). Separately and independently of what any step declares, **any** call on
the `/bff/v1` seam answering `>= 400` during a step is a finding carrying its correlation
id and its body. That last one is `D-5` written as a check rather than as a lesson.

The primitives are self-checking for the same reason: `fill` reads the value back off the
control and throws if React did not take the keystrokes; `attachFile` reads `input.files[0]`
back and compares the size to the file on disk; `click` refuses a disabled or zero-box
control instead of dispatching into nothing. A write primitive that silently no-ops turns a
journey green while exercising nothing — the vacuous pass, one layer down.
