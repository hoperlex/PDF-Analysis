## 5. The five coverage areas, and how each is made structural

**This section describes the contour as round two built it, and it is not rewritten by
later rounds.** Rules added afterwards are described in the round that added them: the
acceptance-evidence rules in §19.9, the two aggregate rules in §19.8, and the declared-size
rule in §20.4. Where a count below says "three rules" or "five obligations", it is that
round's count, and the module's own `LIMITATIONS` and docstrings are the live description.

### 5.1 Terminal state

`classify()` derives the state from the manifest's data and never restates it:
`ratified`, `status`, `current_round`, the current round's own `status`/`verdict`, and
whether a `ratification` record exists. Exactly one of `open-round`,
`closed-accepted-round`, `terminal-ratified` may be satisfied; zero or two is itself the
finding.

The design requirement was that the check **must not go quiet at publication**. In
`terminal-ratified` it still holds five obligations, each of which catches a real
post-publication staleness:

1. the accepted round is the **highest-numbered** round — opening round eleven without
   moving `current_round` is red;
2. both of the accepted round's primary reports **declare a subject commit in their own
   bytes** — a report that binds to a tree only by somebody else's say-so is red;
3. the two declared subjects **agree** — the streams judged one tree or the round is
   void;
4. the manifest's published digests **are the accepted round's own**;
5. every live `CP-00` **status row** states the terminal state and names the accepted
   round — this is the one that goes red the day a later round is accepted and the
   registry is not brought forward.

Attribution for (5) is structural in three parts, all read from the document: the record
must be live, the table must have a **status column**, and the row's **first cell** must
be the checkpoint id. This was arrived at empirically. A prose sweep for
"a sentence mentioning CP-00 and a non-terminal word" was written first and measured on
this tree: **36 hits across 13 files**, of which the great majority were about `ADR-0014`
being deferred, a fixture inside a test module, or a review report quoting a stale claim
in order to report it. That sweep would have been the same defect this programme keeps
making, so it was discarded rather than tuned. The column rule has a recorded negative
case: `README.md:44` carries a `CP-00` row in a roadmap table whose third column is the
checkpoint's *main result*, and it is correctly not a status claim.

### 5.2 Live versus historical, structurally

A record is **historical** when it declares a subject commit *in its own bytes*
(`candidate_commit:`, `Candidate frozen at <sha>`, and the other shapes in
`SUBJECT_DECLARATION`, within the header region), **or** when `manifest.json` binds it to
an acceptance round and that round to a frozen commit. Both sources are data in the tree.
There is **no path list**. `docs/program/reviews/` — which the sweep beside this one
excludes by path, in a narrowing its own acceptance record warned against — is judged
here as live, and a test asserts it is not in the historical set.

The exemption is turned into an **obligation**: a historical record's machine-checkable
claims are **re-derived at the commit it names** rather than skipped. On this tree three
such claims were re-derived and all three hold — `automated-summary.txt` claims 221
tracked paths of `2ea7b68` and `2ea7b68` has 221; `manual-test-report.md` and
`manual-report-round-10.md` claim the same of the same commit. The count is reported in
the verdict header and asserted non-zero, because an exemption nobody pays for is a skip
list with a better docstring.

The two sources are kept **separate** in the API (`declared_subject` and `bound_subject`)
after a defect found during development: conflating them let a report whose header
declaration had been stripped be excused by the round the manifest binds it to, which is
exactly the proximity failure one level up. Obligation (2) in §5.1 asks the report itself.

### 5.3 Tag integrity

The records must agree on **which** tag the checkpoint has; the tag must exist, be an
**annotated tag object**, and peel to a commit.

"Has not moved" is checked against the **digest the manifest publishes**, recomputed at
the tag's own commit. This is not a preference: a recorded-target field is not available
to this checkpoint by construction, because the tag sits on the commit that carries the
manifest and a commit cannot name its own hash — the manifest says so itself about
`manual_candidate_commit`. The digest test has the property that matters: move the tag to
any commit whose reviewed families differ and it goes red.

The **tag message** is the one record whose subject needs no declaration, because an
annotated tag object binds its message to its own commit. Its machine-readable claims are
therefore live claims about the tagged tree, and two of them are false — see §4.

### 5.4 File and hash accounting

Three rules:

* **every file the checkpoint claims exists** — every path-shaped *string value* in the
  live structured bundle records (airtight, no prose), plus backticked **executable test
  artifacts** (`tests/…​.py`) in the live deliverables. The second is a narrowed claim
  shape, not a narrowed sweep: every live deliverable is read, and the narrowing can only
  *add* findings, which is the same reason `MUST_ACCOUNT` is safe in the sweep beside
  this one. It is what catches `CP00-B3`;
* **no aggregate whose members are unlisted** — an aggregate that names a file count must
  enumerate that many per-file hashes, counted by *filename-shaped key* so that an
  aggregate's own value cannot count as one of its members, and counted **at any depth**
  so that a manifest which does enumerate family by family is not read as enumerating
  nothing;
* **no two live bundle records give the same top-level field two values** — top-level
  only, because a value nested under `digest_model` is prose *about* a field qualified by
  its container. This is what catches `CP00-B4`.

### 5.5 Cross-gate agreement

Gates are **discovered**, not hardcoded: any task file whose required-test command reads
a JSON document and asserts on its fields is a gate, and its `assert r['k'] == v` /
`assert r['k'] is v` clauses are extracted and evaluated against that document. Two gates
were found on this tree — `W0-INT-01` and `W0-INT-02` state the same command — and both
disagree with the review on `review_status`.

**This contour does not choose the value.** The finding names both sides and says so in
its own text. Applying the canonical value to
`docs/architecture/CP00_ARCHITECTURE_REVIEW.json` is `W0-INT-02`'s disposition; when it
lands, this check goes green with no edit to any file this task owns.

Two facts were verified independently rather than taken on report, because the choice of
`"ratified"` depends on them:

* `git grep -F -c -- '`ratified`' 92e13fa496a723ed6e4c3adbf138c4f4e1d7c368` → **no
  output, `rc=1`**: the code span appears **zero** times in the reviewed candidate. The
  novelty guard in `_review_consistency_problems` compares the code span, so
  `review_status = "ratified"` is satisfiable and the deadlock that produced
  `ratified_at_w0_3` is gone;
* `test_cp00_candidate.py:5722` already patches the sandbox with
  `review_status="ratified"`, and `:6086` already asserts
  `assertEqual(review["review_status"], "ratified")`. Neither needs changing.

## 6. `tests/contract/test_cp00_candidate.py` — two pinned literals made resolvable

### 6.1 `CHECKPOINT_TAG`, the one the integrator named

`CHECKPOINT_TAG = "v0.0.0-architecture"` was pinned "because a value the integrator can
change is not a value a check can hold them to". The reasoning is right; the literal made
the recovery unreachable. Two guards consume it, no task in the recovery graph except
`W0-QA-04` may write this file, and the recovery ratifies as `v0.0.1-architecture` — so
`W0-INT-03`'s own required `discover -s tests/contract` would fail *at the moment of
ratification*.

Replacing one literal with another only moves the problem to `v0.0.2`, so what is pinned
now is the **series and the rule**:

* `CHECKPOINT_TAG_SERIES = ^v0\.0\.(\d+)-architecture$` — a rename to anything outside
  the series is refused. This is the half of the pin that was load-bearing;
* `CHECKPOINT_TAG_FLOOR = "v0.0.0-architecture"` — the **first** tag of the series. An
  immutable historical fact, not a current value: it was published on an annotated tag
  and cannot be un-published, so the line never needs editing again;
* the resolved value must **agree across all three claims in two records**
  (`manifest.json:tag`, `manifest.json:tag_planned`,
  `contract-manifest.yaml:tag`), match the series, and never move **backward** from the
  floor.

That restores the property structurally: one manifest edit no longer moves the value,
three claims have to move together and the module compares them, a rename is refused, and
a re-tag onto a spent revision is refused. Resolution failure falls back to the floor and
is reported as a **named test failure** rather than raised at import, because an
import-time exception takes the whole suite down and reports nothing about why.

The anti-gutting needle in `RATIFICATION_PUBLICATION_RECORDS` — which required the W0.3
wave plan to still contain the literal `` `v0.0.0-architecture` `` — became a **shape**,
`re:` + the series body. Its job is to refuse a retraction made by deleting what the
stale claim was about, and a plan naming `v0.0.1-architecture` is not gutted. The needle
is a *marked string* rather than a compiled pattern for a reason worth recording: a
compiled pattern is a call to an attribute, `_is_a_literal_expectation` refuses one, so a
table holding a compiled pattern **could not be pinned at all** and
`TableExpectationTests` would have gone quiet on the whole table to accommodate one entry.
The marked string keeps the shape and keeps the table pinned whole. That failure was
observed, not predicted: the first version of this change turned
`test_every_table_this_module_defines_carries_a_literal_expectation` red.

### 6.2 `WriteBoundaryTests`, a second one of the same shape, found by doing the work

`test_only_the_two_owned_paths_are_reported_under_the_owned_trees` pinned the owned set
to `W0-QA-01`'s two files and required nothing else under `tests/contract/` or
`docs/program/reviews/` to be dirty. It is a **task-local containment gate that outlived
its task**: committed into the shared suite, it turns red for every later task licensed
to write in either tree. `W0-QA-04`'s allowed paths name
`tests/contract/test_cp00_final_state.py` and `docs/program/reviews/W0-QA-04.md`, so with

same shape as `CHECKPOINT_TAG`, and the same shape as round nine's "performing the
ratification voids the round that authorises it". It was not predicted; it turned red the
moment the deliverable was written.

The repair keeps the property and drops the pin: a dirty path is contained when **some
task file's own `## Allowed paths` section declares it**, read out of
`docs/program/tasks/`. That is not the weakness the module warns about — a directory
listing grows when anybody adds a file, whereas this grows only when somebody writes a
task that claims the path, in a document that names an owner and goes through the same
review as the work it licenses. The scan finds declarations in all 20 task files;
`_path_is_declared` is asserted to **refuse** an undeclared path, so containment still
proves something.

## 7. What did not hold, plainly

### 7.1 The contract's two clauses are inconsistent on this tree, and the red was chosen

`Required tests` says `discover -s tests/contract` must exit `0`. `Integration contract`
says a tree "whose claimed artifacts do not exist, or whose two ratification gates
disagree, turns at least one named check red". **On this tree both cannot be true.** The
gates do disagree, the claimed test modules do not exist, and choosing `review_status` is
explicitly `W0-INT-02`'s and forbidden to me.

Three ways out were considered and two rejected:

* `unittest.expectedFailure` on the cross-gate test. Rejected: it makes the contour
  silent *while the gates disagree*, which is precisely backwards, and Python turns an
  unexpected success red — so it would go red the moment `W0-INT-02` fixed it;
* a recorded ledger of open findings that the test compares against. Rejected: it is red
  only for findings nobody wrote down, and `tests/**` is `W0-QA-04`-owned in phase A, so
  `W0-INT-02` could not remove an entry after fixing it. A check that is quiet about a
  contradiction because somebody wrote the contradiction down is the failure mode this
  checkpoint has spent ten rounds on;
* **chosen:** the check is red, named, and self-closing. It names both sides, names the
  owner, and goes green with no edit to any file this task owns.

The exit code is reported honestly in §3.6 rather than engineered to `0`. Note also that
the command already exited `1` at the base commit for an unrelated and unowned reason
(§3.6), so "exit 0" was not achievable on this tree before this task started either.

### 7.2 The tag's target commit is not recorded anywhere, and cannot be

"Has not moved relative to its recorded target" cannot be checked against a recorded
target for CP-00: the tag is on the commit that carries the manifest, and a commit cannot
name its own hash. The digest reproduction in §5.3 is what replaces it and it has the

### 20.5 F4 — what report reading catches, and what it does not

Two weaknesses, and they are not the same kind, so they did not get the same remedy.

**The placeholder rule was upper-case only, and it is the load-bearing half.** Measured on

Any rule accepting all five is satisfiable by ordinary prose, so what this check catches is
one thing: **a report that states no result vocabulary at all**. That is now recorded in
the module's `LIMITATIONS` (the eighth), in §7.3, in the function's own docstring and in
§19.9 — and it is pinned from both sides by
`test_the_verdict_rule_reads_presence_and_not_position`, so the description and the guard
cannot drift apart silently: a sentence about another round's `PASS` is accepted, and a
report with no token at all is a finding.
