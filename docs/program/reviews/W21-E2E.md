## 2. The journey's shape and what it records

`tests/e2e/pc01/journey/` — three files and a fixture, 1 013 lines:

* **`manifest.json`** — the journey written down **once**, read by two checkers that never
  consult each other: seven routes, the `page_module` behind each, the API calls each must
  make (`expects_api`) and may make (`optional_api`), and a `follow` rule naming the link
  that yields the next identifier.
* **`cdp.mjs`** — a Chrome DevTools Protocol client over Node 22's built-in global
  `WebSocket`. It exposes `withColdBrowser(fn)` **and nothing else**.
* **`journey.mjs`** — the walk, the assertions, the envelope.
* **`fixtures/redden.manifest.json`** — a deliberately wrong manifest, see §3.

**What it records, per request, for every request — not only the interesting ones:** method,
URL, resource type, the request headers that matter, the request body, **whether the request
carried an `Authorization` header** (presence only, never the value), status, status text,
the response headers that matter — `content-type`, `x-correlation-id`, `location`,
`cache-control`, … — and **the response body**, fetched from the browser before its process
ends. Per route it also records what the page rendered as text, every link it offered, its
console errors, any uncaught exception, the full redirect chain, and the navigate / settle /
body-collect timings.

Measured against the deployed alpha at `http://127.0.0.1:31500`: **7/7 routes, exit 0,
178 s, 134 exchanges, a 3.6 MB envelope.**

```
ok  root       200  api=1 auth=0   307 http://.../  ->  200 http://.../projects
ok  projects   200  api=1 auth=0   {"project_uid":"prj_01M2TB4Q17RBFKHQ17SP1QYMFR"}
ok  project    200  api=1 auth=0   {"document_uid":"doc_01M2TB4QM2S5NZVXFTT1EJVSX6"}
ok  document   200  api=1 auth=0   {"version_uid":"ver_01M2TB4QM517ZXWD3NWWS2QMJ2"}
ok  version    200  api=2 auth=0   {"run_id":"run_01M2TB4QP6B784MQ7NN1TFFP79"}
ok  run        200  api=1 auth=0
ok  review     200  api=5 auth=0
```

Every one of those four identifiers was **discovered by following a link the page actually
rendered**. Nothing was handed in: the journey is given an origin and nothing else. That is
also the strongest rendering assertion in it — a screen that renders no link to its children
fails the route that needed it, and the walk **stops** rather than reporting on routes it
never reached.

`auth=0` on every route: no browser request carried an `Authorization` header, so `T-6`'s
seam — the credential lives in the BFF handler, server-side — held under a real browser.

The envelope is the point. One line of it:

```
200 GET /bff/v1/findings/fnd_01M2TB4R80CJ8SQ776S25YGM0W/decisions
    x-correlation-id: cid-485f8036ab0bc526850c214ed6820111
    content-type: application/json
    body[44]: {"items": [], "page": {"next_cursor": null}}
```

`D-5` closed unanswerable because its harness had the first line and none of the rest.

**Cold loads, preserved by construction.** Every route is visited by a **separate
operating-system browser process with its own throwaway profile** — no cache, no storage, no
cookies, no prior client state. `cdp.mjs` offers no API for reusing a browser, so the
property `D-16` was missed by cannot be lost by forgetting it. **It costs almost the whole
run time**: in a warm browser the same navigation takes 16 ms against 3.8–25 s for the first
navigation in a fresh process. Reusing one browser would make this roughly ten times faster
and would stop it being able to find `D-16`.

**The gate-side guard.** Seven negative controls in
`tests/e2e/test_pc01_journey_conformance.py`, one per check: an unwalked screen, a deleted
screen, a renamed dynamic segment, a renamed operation, a changed method, a missing input
that must fail rather than skip, and — because set arithmetic is only worth as much as the
scan feeding it — a synthetic app tree proving `screens_in_app_tree` finds nested and dynamic
screens and ignores route handlers. They read nothing outside the file.

One of those controls was itself vacuous when written: `pytest.fail` raises `Failed`, which
derives from `BaseException`, so `pytest.raises(Exception)` let the failure straight through.
Caught by running it.

## 4. Is the instrument inside the tree? Plainly: yes.

**`web/package.json` changed by one line. `web/package-lock.json` is untouched. No
dependency was added.**

`cdp.mjs` speaks CDP over Node 22's built-in global `WebSocket` — Node 22.23.1 is already
pinned in `web/package.json` `engines`. The four domains it uses (`Target`, `Page`,
`Network`, `Runtime`) are the stable, documented half of the protocol.

The brief said that following `W15-RUN`'s precedent — `playwright-core` installed outside
the repo, imported by absolute path — would mean `D-5`'s real problem was **not** fixed,
because the instrument would still be outside the tree. That is right, and it is why I did
not follow it. The alternative on offer was to add `playwright-core` to `web/package.json`;
that would have been one new repository dependency, and a finding to report. Neither was
needed.

**What is still outside:** the Chromium *binary*. That is an environment prerequisite, like
`docker` or `npm`, not a repository dependency. It is searched for in five usual places,
`E2E_PC01_CHROME` overrides, and an absent browser is a hard failure with instructions —
never a skip.

**What this cost:** ~490 lines of protocol client the programme now owns, and four defects
in it that only running it found (§6). A dependency would have bought those lines back at
the price of the thing the whole task was about.

## 5. Where it runs, what stops it rotting, and what that costs

**It runs beside the gate**, under `npm --prefix web run e2e:pc01`, not inside it.

The argument is from the tree, not from taste. `make gate` already depends on a stack — it
is `gate: foundation`, and `foundation: up …` starts PostgreSQL and MinIO. What it does
**not** depend on is a **built web image and a bound HTTP port**, and that is the line I did
not cross. `run_frontend`'s own comment says why the line matters: *"The frontend is a
delivered part of PC-01 and four waves passed without it being run once, because no target
named it."* A gate that additionally needed `docker compose up` of the app, a Next.js build
and a free port is a gate that gets run with `-k` or skipped, and then all of it stops
meaning anything. `OD-16` independently forbids adding a `Makefile` target for the frontend,
so the invocation had to be an npm script regardless — and I did not touch the `Makefile`.

**What stops it rotting** is `tests/e2e/test_pc01_journey_conformance.py`, which runs
**inside** `run_battery` with no browser, no origin, no port and no service. It checks
`manifest.json` against two things the journey does not author:

1. the route tree under `web/src/app` — **every** screen, and only screens that exist;
2. `contracts/api/v1/openapi.json` — every `(method, path, operationId)` triple it declares;

plus that each route's path agrees with its own `page_module`, and that the BFF is still
mounted where the manifest addresses it.

Add a screen and the gate goes **red until the journey walks it**. Delete a screen, rename a
dynamic segment, rename an operation, change a method, move the BFF mount: red. That is the
"something must fail" the brief asked for, and it is not "someone will remember".

**The cost, stated rather than left silent — three parts:**

* **The guard checks addressing, not behaviour.** A screen whose route and API calls are
  unchanged but which renders nothing is invisible to the gate and visible only to the
  journey. Keeping the gate stack-free buys exactly that blind spot.
* **The journey still only runs when someone runs it.** Nothing in this session makes a
  wave *fail* for not having run it. What the guard guarantees is narrower and honest: the
  journey cannot silently stop *addressing* the product.
* **`make gate` got slower by the eleven tests this adds** — 0.02 s. That part is free.

There is also a cost in the other direction I should name: `npm run e2e:pc01` now **exits 0**
while `P3-QA-01`'s task specifies idempotency, negative, leakage, restart, byte-identity and
anti-vacuity specs that are **not here**. A green from a partial suite over-stating itself is
`D-23` in a different costume. `README.md` says so in its own section, and this review says
so here, but prose is the weaker mitigation and I am flagging it rather than claiming it
solved.

## 6. Defects found by running it

Four in the instrument, each fixed with the measurement kept in the comment:

1. **A redirect reuses the CDP `requestId`.** Incrementing the in-flight count on the second
   `requestWillBeSent` left it permanently above zero, so every navigation waited out the
   full settle timeout. The hop's own `307` and `Location` were also being overwritten — the
   same status-line impoverishment as `D-5`, one level down. Both fixed; the redirect chain
   is now recorded hop by hop.
2. **`Network.getResponseBody` never answers for a request the browser has not finished.**
   It does not error. It hangs.
3. **`collectBodies` iterated the live exchange list.** The run screen polls, so the list
   grew at least as fast as it was consumed and that route never ended.
4. **The review screen's PDF pane opens a `blob:` URL and Chrome's built-in viewer**, both
   reported as documents. Taking the last document as the landing page meant the route's
   verdict came from the viewer rather than from the application.

Two about the application, not the instrument:

5. **`/projects/<anything>` answers 200, not 404.** The dynamic segment matches any string,
   so an unrouted project path renders the project screen in an error state; only an unrouted
   *top-level* path 404s. Confirmed by `curl`. Consistent with `W19-SHELL`'s
   `project-unknown` → 200. **It means a 200 does not by itself distinguish a screen from a
   soft error**, which bounds what this journey's status check proves.
6. **No Next.js route here is ever network-idle**: at least one request per screen never
   emits `loadingFinished`. Settling on *quiet* rather than on *empty* is what makes the
   journey finish at all.
