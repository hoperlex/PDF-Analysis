# Два модуля сравнения — показ на 7 минут

Сценарий для уже подготовленного **локального синтетического стенда**, прочитан по исходникам `cmp-int` на `01d76dff` 30 октября. Браузерный прогон этого сценария не выполнялся. Все документы вымышлены. Время загрузки и расчёта не входит в семь минут: оператор заранее получает готовую матрицу VS-1 и завершённый полный запуск SP-1 через существующие controls/helpers.

Показываем работающие детерминированные сравнения VS-1 и цепочку SP-1 с синтетическим ответом C4, решением эксперта и журналом. ИИ-описание VS-1 и его Markdown не входят в этот исполняемый маршрут: готового C2 recorded worker для него нет. Код C2 требует настроенного исполнителя либо отдельного source-bound recording; C4 helper их не подменяет.

## Перед показом

API, UI и процессы обработки должны использовать один кандидат. Версия продукта в прочитанном дереве — `0.9.0`, API — `1.13.0`, migration head — `0043_stage_ai_generations`; это не подтверждение версии какого-либо развёрнутого стенда. Войти учётной записью с ролью `expert` и выбрать отдельный тестовый проект. Роль `admin` без `expert` не даёт прав на экспертные действия.

| Процесс / фаза | Настройка |
|---|---|
| API, весь показ | `AUDITMANAGER_COMPARISON_MODULES=versions,stages`; `AUDITMANAGER_PROVIDER_MODE=recorded` |
| Обычный worker, подготовка VS-1 | `AUDITMANAGER_COMPARISON_MODULES=versions`; `AUDITMANAGER_PROVIDER_MODE=recorded`; тот же кандидат и DB/S3 |
| Обычный worker, подготовка/показ C4 | comparison-модули `none`: он не должен забирать stage recorded work |
| Явный C4 helper | команда ниже; внутри обслуживает stage AI и shared intake/profile work с `versions,stages`; registry version `synthetic-c4-journey` |

Флаг на API управляет меню и операциями; worker должен обслуживать нужные типы работ. Обычный worker с `none` не построит матрицу/series VS-1. C4 helper тоже не обслуживает `matrix_build`/version series: сначала подготовить VS-1 обычным worker, затем переключить обычную comparison-обработку на `none` и использовать C4 helper. Нового стенда или seeder для этого сценария не нужно.

Существующая команда обычного worker, в окружении уже назначенного локального стенда:

```sh
EXECUTION_ROLE=worker AUDITMANAGER_PROVIDER_MODE=recorded \
AUDITMANAGER_COMPARISON_MODULES=versions PYTHONPATH=src \
  .venv/bin/python -m auditmanager.workers serve
```

Команда существующего C4 helper из [journey README](../../tests/e2e/pc01/journey/README.md), **после подготовки VS-1**. `DATABASE_URL` и `S3_ENDPOINT_URL` уже должны указывать на тот же локальный стенд; helper принимает только loopback endpoints. Он не предназначен для внешнего сервера.

```sh
AUDITMANAGER_PROVIDER_MODE=recorded PYTHONPATH=src .venv/bin/python \
  tests/e2e/pc01/journey/c4_recorded_worker.py --local-synthetic-only --seed-route \
  --receipts /tmp/c4-synthetic-receipts.jsonl
```

`--seed-route` — уже существующая настройка тестового маршрута helper, запускается оператором один раз для подготовки локального показа. Это не импорт документов: PDF, пары, сборка, связи и решения проходят собственные UI-команды продукта. Если используется maintained journey, передать ему `E2E_C4_RECORDED_RECEIPTS=/tmp/c4-synthetic-receipts.jsonl`; запуск journey не является частью этой docs-задачи. Helper записывает фактические request/source/run digests и SHA реальных PNG, не вызывает внешнюю модель. Имя маршрута в нём — `Synthetic C4 journey fixture`.

## Точные данные и подготовка через интерфейс

**VS-1:** [v1.pdf](../../fixtures/comparison/vs1/v1.pdf), [v2.pdf](../../fixtures/comparison/vs1/v2.pdf), [v3.pdf](../../fixtures/comparison/vs1/v3.pdf), [v4.pdf](../../fixtures/comparison/vs1/v4.pdf), [v5.pdf](../../fixtures/comparison/vs1/v5.pdf). Ключ — [vs1/answer_key.json](../../fixtures/comparison/vs1/answer_key.json), описание — [comparison README](../../fixtures/comparison/README.md). Один комплект `СИНТ-01-ЭМ`, версии `Изм.0`…`Изм.4`, 6/6/6/6/8 страниц.

На `/version-comparison`: выбрать проект → «Загрузить проект со всеми версиями» → добавить пять PDF в порядке V1…V5 → «Загрузить и разобрать» → проверить один комплект и порядок → «Подтвердить группировку и порядок». Открыть комплект кнопкой его названия → «Подготовить» → дождаться готовой матрицы → в блоке «Сравнение соседних» нажать «Запустить» и дождаться четырёх завершённых переходов. Не запускать ИИ-шаги VS-1 без отдельного готового C2 исполнителя. На показ оставить готовую матрицу и переход V1→V2.

**SP-1:** [old_p.pdf](../../fixtures/comparison/sp1/old_p.pdf), [new_r1.pdf](../../fixtures/comparison/sp1/new_r1.pdf), **[sp1-new-r2-graphic.pdf](../../tests/e2e/pc01/journey/fixtures/sp1-new-r2-graphic.pdf)**, [new_r3.pdf](../../fixtures/comparison/sp1/new_r3.pdf). Ключ исходного SP-1 — [sp1/answer_key.json](../../fixtures/comparison/sp1/answer_key.json). Для Р2 здесь используется уже подготовленный journey derivative вместо исходного [new_r2.pdf](../../fixtures/comparison/sp1/new_r2.pdf): добавлен один круг, чтобы существовал реальный графический crop. Generator [make-sp1-graphic.py](../../tests/e2e/pc01/journey/fixtures/make-sp1-graphic.py) и manifest фиксируют происхождение; исходный SP-1 не изменён. Не приписывать добавленный круг исходному answer key.

На `/stage-comparison`, вкладка «1. Загрузка документации»: каждый PDF → «Загрузить новый набор» → «Стадия» П для OLD, Р для трёх NEW; «Раздел» АР; шифры `СИНТ-02-АР`, `СИНТ-02-АР.1`, `.2`, `.3` → «Подтвердить документ». Раскрыть «Создать сборку Р и связать со стадией П» → выбрать документ П и все три Р → назвать сборку `SP-1 · Р1 + Р2 + Р3` → «Создать сборку» → «Подтвердить пару П ↔ сборка Р». Получаем шесть листов П и 3+1+2 листа Р; статусы полноты остаются явным решением эксперта.

Вкладка «2. Сопоставление листов» → «Принять видимые точные подсказки» → «Сохранить решение эксперта». Пять листов имеют точную пару; по одному листу с каждой стороны остаются без пары. Для необязательного показа repair/undo использовать уже существующую подготовку `swapped_map` из [stage-c4.mjs](../../tests/e2e/pc01/journey/stage-c4.mjs): переставить первые две связи через selectors и сохранить. Не менять opaque IDs или строки SQL вручную.

«С описанием изменений ИИ» → «Запустить полное сравнение» → проверить в оценке `recorded`, объём и текущие изображения → поставить «Подтверждаю передачу указанных данных выбранному исполнителю и оценку стоимости.» → «Подтвердить». При остановке на следующем окне: «Продолжить», прочитать новую оценку, дать новое согласие. Дождаться «Завершено» и шагов 1–7: связи → одинаковый текст → расхождения → ИИ-ревизия → классификация/починка → синтез → карточки. Для семиминутного показа завершить это заранее; не обещать конкретную скорость расчёта.

Все ID выбираются из UI; URL не собирается из названия файла или номера листа.

## Как назвать синтетический ответ

В оценке C4 уже есть строка «Подключение использует записанные тестовые ответы.». Показать её при подготовке либо открытии новой оценки и сказать: **«Здесь режим recorded. Конкретно этот локальный helper формирует синтетический ответ по фактическому входу; это не запись ответа реальной модели. Мы показываем проход данных, свидетельства, решение эксперта и экспорт».** Оценку можно закрыть кнопкой «Отмена», не начиная новый расчёт.

В карточках показать настоящий заголовок «Синтетический ответ требует проверки» и метку «не подтверждено инженером». Helper намеренно выдаёт `UNCERTAIN`/`REVIEW`, `materiality=unknown`, `importance=unknown`, а обобщение — `INSUFFICIENT_CONTEXT`. Он не демонстрирует качество инженерной классификации, высокую важность, принятие моделью решения или доказательство отсутствия объекта. Реальные детерминированные PDF/crops/очередь/история/выгрузки при этом используются без подмены. Наличие PNG receipt — доказательство передачи тестовому adapter фактических изображений, а не вызова внешней модели.

В этой задаче проверены только существование перечисленных source paths и соответствие controls/helpers исходникам, плюс whitespace. Скриншоты не добавлены. Полный браузерный маршрут, live-качество и тяжёлые окна остаются отдельной от презентации проверкой.
