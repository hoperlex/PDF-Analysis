## How the system is called

- **API:** the served application (`create_asgi_app` through the suite's `Surface`) over the
  **shipped** `CredentialAdapter`, `AccountAdapter` and `RegistrationAdapter`
  (`identity_surface`), so the seam decides on the row's standing. Credentials come from the
  real `issueToken` wherever sign-in is under test, and from the suite's signer at the row's
  epoch elsewhere.
- **Sequential claims** run in the API suite's rolled-back transaction.
- **Races** run on a **fresh database migrated to head** (the `db` suite's `migrated_engine`,
  re-exported by `tests/integration/api/qa_w49/conftest.py`), with real commits: a blocker
  transaction holds `FOR UPDATE` on the rows the operations must lock, both HTTP requests are
  started on two separate applications, the helper waits until `pg_stat_activity` shows both
  backends waiting on a lock — i.e. both have passed the seam — and only then releases them
  (`qa_kit.race`). Every race test asserts it was forced, and then asserts the outcome, never
  the interleaving.
- **BFF:** the real route handler with real `Request` objects; `fetch` stubbed by address and,
  for item 4, by credential, so two people can be signed in and only one loses a role.

## Open questions (for a ruling; not decided here)

**Q-1 — through the BFF, one sign-in attempt by a pending applicant spends two units of the
request's brake, and the correct password on the third try is refused and shuts the request
for five minutes.**

- Where: `src/auditmanager/access/repository.py:588-602` (`authenticate` counts a failed
  exchange for a login no active account holds on that login's request,
  `_NOTE_A_FAILED_REQUEST_ATTEMPT`) together with `src/auditmanager/access/registrations.py:536-557`
  (`read_status` counts its own refusal, `_note_a_failed_read`) and
  `web/src/app/bff/v1/[...path]/route.ts:649-654` (a refused exchange is always followed by
  the status read with the same pair). `FAILED_SIGN_IN_ALLOWANCE = 5` and
  `COOLING_OFF_SECONDS = 300` (`access/repository.py:166`, `:182`).
- Reproduction (API, the BFF's call shape, measured on `d2ab3c7` with a throwaway probe that is
  not committed): submit an application; twice call `issueToken` and then
  `readRegistrationStatus` with the same wrong password (count after: `4`); then call both with
  the **correct** password. The exchange is refused (no account) and counted (`5` ≥ allowance:
  `sign_in_blocked_until` set), so the status read finds the request braked and answers the
  generic `401`. Through the BFF that is `/login?refusal=credentials` for the right password,
  and five minutes of refusals after it.
  The probe, placed temporarily in `tests/integration/api/qa_w49/` and deleted after the run
  (helpers from `qa_kit.py`):

  ```python
  login = fresh_login("probe"); assert submit(surface, login).status == 201
  for i in range(2):                       # two wrong sign-ins, as the BFF makes them
      exchange(surface, login, f"wrong-{i}"); status_read(surface, login, f"wrong-{i}")
  # failed_sign_ins == 4
  exchange(surface, login, PASSWORD); status_read(surface, login, PASSWORD)
  ```

  Output: `after 2 wrong BFF attempts: 4`, then `right pair third attempt: exchange 401 status
  401 … count 5 blocked True`.
- Why it is a question and not a finding: §3.3 says "the request's throttle columns count both
  kinds of attempts" and §3.5 says the BFF makes both calls after a failed exchange; the
  composition of the two sentences produces exactly this, and no sentence of the plan says one
  human attempt must cost one unit. Against it: the access module states the request brake
  follows "the account brake's rules (`W40-LIMIT`)", under which a correct password presented
  outside a block is never counted as a failure, and an account gets five mistakes where a
  pending applicant gets two.
- An observation for the ruling: the exchange never compares the pair with the request's
  digest (`authenticate` spends one derivation with a throwaway salt, `passwords.py:224`, and
  returns `None`), so counting a failed exchange on the request protects no secret — the
  status read is the only place the request's password can be guessed, and it already counts
  its own failures. What the extra count buys is a second way to brake the request; what it
  costs is the applicant's allowance.
- Possible rulings: accept and register it; or stop counting failed exchanges on the request
  (the status read alone brakes it); or give the request a larger allowance. Each is a change
  to `access`, outside this task.

**Q-2 — the last-administrator rule is reachable through the served operations only as a race.**
The seam admits `updateUser`/`archiveUser` only to an account holding `admin`, and the actor is
never the target (that is the self rule), so a sequential request always leaves the actor as a
second administrator. Item 3 is therefore tested as a race through the API and sequentially
below the router; the plan's "through `updateUser` and `archiveUser`" is read that way. No
change is proposed; recorded so a reader of the brief knows why there is no sequential API test.
