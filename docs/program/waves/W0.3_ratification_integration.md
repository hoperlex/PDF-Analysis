## Scope

- Specify the architecture lint rules required by `U-03` without implementing a
  linter.
- Complete `ID-01` in strict order: validator reads `contract_version`, domain removes
  its deprecated mirror, events replace `schema_version` with `contract_version`.
- Add independent consumer-style checks across architecture, domain, analysis,
  events and the golden baseline without changing those artifacts.
- Reconcile point-in-time statements in the CP-00 review with the accepted final ANA
  precondition and record the ratification act.
- Produce the CP-00 evidence bundle and run the complete manual acceptance script.
- Fast-forward the accepted integration branch to `main`, then create and push the
  annotated registry tag `v0.0.0-architecture`.

## Recorded exceptions — integrator writes outside a task's allowed paths

### One — integrator edits bundled inside three task commits

The CP-00 automated audit found that three integrated commits touched a path outside
the task's declared `allowed_paths`: `3ca8e25` (`W0-EVT-01`) and `854a682`
(`W0-QA-01`) each carried an edit to their own task file, and `92e13fa`
(`W0-CLN-01`) carried an edit to `W0-ARC-02.md`, another task's file.

No agent exceeded its boundary. Every author's `git status` proof was accurate at
hand-off; the integrator bundled his own task-specification corrections into the same
`git add` and so widened the task's diff after the fact. The edits are gate and
status text, not contract, fixture or test content, and each independent reviewer
accepted the artifact bytes it actually reviewed.

The repository owner recorded this as an accepted exception on 2026-09-02, to be
examined at stage closing rather than by reopening three accepted tasks — which would
invalidate three independent `ACCEPT` decisions over text their authors never wrote.

The procedural correction stands for every later wave: **integrator edits to task
specifications go in their own commit, always.** The integrator did this correctly six
times in this wave and incorrectly three times; the wave's own gate list already
requires that each task's diff be a subset of its `allowed_paths`, and that gate is
what caught it.

### Two — integrator writes into an accepted task's own deliverable

`afe1895` and the round-eight remediation both edited
`docs/program/reviews/W0-QA-01.md`, a `W0-QA-01` deliverable, after that task was
accepted. The path is in no other task's `allowed_paths`, `W0-INT-01`'s included.

A review report structurally cannot name the commit that contains it, so section 1
named its predecessor as the live evidence commit; that became false the moment round
twelve was integrated, and sections 12.1 and 12.5 repeated it. Section 12.5 of the
report is itself a handoff instructing the integrator to make exactly this correction
after exactly this event, so the edits follow the accepted handoff rather than
overriding it. They change no verification claim, and each is labelled as the
integrator's in the text where it appears.

This is a **different shape** from the three above: not a task-specification
correction bundled into a task commit, but a write into an accepted task's own
deliverable, in its own commit. The count above is unchanged — `afe1895` and the
remediation each went in their own commit, which is what that count measures.

Two acceptance rounds failed on the residue of the first of these edits. `afe1895`
declared its sweep exhaustive and was not: it corrected section 1 and left sections
12.1 and 12.5 thirty-six lines away, and it introduced two new false statements while
fixing one — `e7f3989` carries rounds two to six, not two to eleven. The round-eight
remediation replaced that declaration with a check that can fail: a context-aware sweep
over every tracked file requiring each occurrence of a superseded commit to be either
committed acceptance evidence or labelled superseded within three lines. Raised for the
stage-closing review with the three above.

## Manual/checkpoint impact

The manual tester executes all six cases in
`docs/manual-tests/CP-00_architecture.md` against one recorded candidate commit. Any
`FAIL` or unexplained `BLOCKED` stops ratification and prevents the tag. `U-04`,

## Stop conditions / rollback

- Stop on a new semantic disagreement, unowned contract write, mixed contract version,
  non-reproducible documented gate, unresolved cross-family reference or manual
  acceptance failure.
- A defect before freeze is fixed in the owning task and re-reviewed; downstream
  commits are rebuilt from the corrected integration point.
- After ratification, any contract change follows the formal freeze-break procedure.
- A failed push never changes the local acceptance decision; reconcile the remote
  branch without force-pushing or rewriting accepted history.
