## Implemented in this candidate

- The seven stage-pair operations are served when `AUDITMANAGER_COMPARISON_MODULES=versions,stages`. The module-off answer remains typed `503 dependency_unavailable`.
- Pair suggestions read the newest version's effective expert classification. They emit a nonbinding П→Р hint only for a unique section and normalized designation or title on both sides. A confirmed designation on both sides scores `1.0`; a display-title fallback scores `0.75` and says so in its reason. Names never become pair identities.
- A keyed expert command confirms one П document against one Р document or a Р assembly in the same project and section. It serializes active binding decisions per project, refuses a second active pair for the П document, and replays the original command ID.
- Р assemblies have append-only member rows. Their creation and revision use distinct derived command records per member; a revision checks its `base_member_no` and leaves removed members as history. The pair references an assembly identity rather than a name or a document list.
- The keyed completeness command writes the current choice and an append-only `audit_event` with the prior choice, new choice, actor and command identity in the same transaction.
- The ZIP intake helper bounds a nonseekable raw stream before extraction: declared byte cap (2 GiB), measured size and SHA-256, one active admission, and free disk for both raw spool and maximum extracted set plus 512 MiB reserve. It passes the production set policy and comparison PDF envelope; an invalid member refuses the entire set and both temporary layers are cleaned.
- A stage upload declaration creates the batch and file rows in one keyed transaction. It enforces the 2 GiB raw budget, 1,000 file count and the active-upload limits under an installation advisory lock. The read side returns opaque file and candidate identities. All ten sealed upload operations now reach these services through the composed adapter only with `versions,stages`.
- The part writer records a content-derived Blob declaration, a multipart token and a declared part under a keyed command **before** it sends bytes to the store. A receipt commits only after storage reports the exact measured size and digest. A storage refusal removes the declared part so a new keyed attempt can resend it. A process lease lets a new key replace a stranded declared part after its writer dies; the old key stays stale. The same batch lease serializes part writes and raw completion with pause/cancel.
- Raw multipart completion verifies the contiguous receipts and declared size before asking the store to assemble. A `stage_raw_completion` command records this internal checkpoint separately from the public completion receipt. The Blob moves through committed `temporary → verifying → available` metadata; if the process loses the publish response, a lookup by its content-derived Blob ID resumes without uploading again. The raw file is then `received` with a write-once Blob reference. PDF/ZIP admission has not begun at this point.
- The admission service claims the installation's sole active admission in PostgreSQL and holds a separate PostgreSQL session lease while it reads bytes. A dead process releases the lease, so the next attempt can reset a stranded `admitting` row; a live second attempt is refused. It measures free space on the reader's temporary filesystem, streams the immutable raw Blob through the bounded ZIP reader or the production comparison PDF envelope, and inserts all candidate rows in one transaction **after** every PDF passes. Candidate facts retain each member's digest, size and a publication token for later recovery. A refused ZIP, including `__MACOSX/` in raw or Unicode Path names, leaves zero candidate rows and no temporary extraction. The served completion operation invokes this admission after raw Blob verification.
- The candidate decision service records an expert's keyed confirmation or rejection with an audit event. Confirmation checks project ownership, section and current classification when it binds an existing document. Before any ZIP member reaches object storage, the publication service commits the candidate's immutable content facts and a content-derived Blob metadata declaration; the candidate's `pdf_blob_id` is bound only after the Blob is available, so reference audits see settled FKs. It reopens and revalidates the whole ZIP, verifies the selected member, and can continue from a temporary or already canonical Blob after process failure. The document, comparison-only version, classification and published candidate commit in one DB transaction. A plain PDF reuses its already verified raw Blob.
- Pause and resume are keyed owner commands. Cancellation commits the cancelled batch and file states before aborting staged multipart tokens. The write-once tokens remain the cleanup journal: replay and `sweep_cancelled` repeat abort safely after a store refusal or process crash. `python -m scripts.recovery.stage_upload_cleanup` is the repeatable recovery entrypoint; its page size bounds each DB read. Confirmed or published candidates prevent cancellation.
- The registered `/stage-comparison` screen shows a paged catalog of confirmed pairs and nonbinding suggestions. An expert can open a decision panel for one suggestion and set a confirmed pair's completeness; an administrator can read but has no decision controls. The link from «Сравнение версий» is shown only when `versions,stages` is served. The new screen is out of the static navigation menu, so a module-off deployment has no stage menu item.
- The same screen now shows project upload batches, one-file PDF/ZIP selection, 16 MiB part transfer, retry against declared SHA-256 and size, cancellation, and candidate confirmation/rejection. The browser hashes one 1 MiB slice at a time; a failed request retains its key within the current screen session. A page reload needs the user to choose the same file again. The UI names a stage, section and designation only as an explicit expert decision; a display name remains a hint.
