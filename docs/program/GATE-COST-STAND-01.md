# GATE-COST-STAND-01 — измеренное сокращение тестового ожидания

Задача: `docs/program/tasks/GATE-COST-STAND-01.md`. База:
`19658de9e1dacbaa8a944489249a1153518af377` на локальной
`integration/gate-opt-01`. Изменение касается только fake-Docker теста
`database-ready`; полный `make gate` по `R-135` остаётся за финальным
beta-кандидатом.

## Что показало профилирование

| Проверка на базе | Результат | Вывод |
| --- | --- | --- |
| Весь `test_stand_copy_refusals.py` | 146 passed, 1 ожидаемо skipped, 5 предупреждений, 75.44 с; `database-ready` 7.92 с | Файл дорогой, но одна задержка управляется только тестовым timeout. |
| 36 `copy-serve` guard cases | 36 passed за 21.81 с; наиболее долгие 1.72 и 1.58 с | Большая часть времени — выполнение сценариев с shell/stub, не подготовка стенда. |
| Три прямых замера `_stage` | 0.011–0.015 с на стенд; запуски shell занимали 0.017–0.822 с на выбранных случаях | Кэшировать staging в этом семействе ради скорости нет смысла. |
| 70 архивных negative fixtures | `build()` суммарно 0.025 с; product `judge()` 1.891 с; независимый validator 0.049 с | Гипотеза предыдущего аудита о выигрыше от общего создания архива не подтвердилась; кэширование дало бы лишь миллисекунды. |

`restore-test.sh` берёт `STAND_COPY_RESTORE_READY_SECONDS` из окружения
теста. При `ready=False` прежнее значение `2` заставляло и оригинал, и
мутант пройти лишние секундные ожидания. Только для этого case установлен
`0`. В обоих вариантах тест теперь дополнительно утверждает ровно один
вызов `pg_isready`: проверка готовности не обходится. Исходный script,
stub-ответ, отказ `database-ready`, мутация с удалённым guard и остальные
146 случаев не изменены.

## До и после

Один и тот же pytest node с `--durations=20`, на том же checkout/host:

| Прогон | До, `call` | После, `call` |
| --- | ---: | ---: |
| 1 | 8.08 с | 3.99 с |
| 2 | 8.03 с | 4.16 с |
| 3 (полный файл до изменения / адресный после) | 7.92 с | 4.18 с |
| Медиана | **8.03 с** | **4.16 с** |

Медиана этого случая сократилась на **3.87 с (48.2%)**. Прогон всего файла
после изменения: **146 passed, 1 skipped, 5 предупреждений за 98.47 с**;
изменённый case в нём занял 4.50 с. Это **не доказательство ускорения всего
файла**: он занял больше wall time, и времена нескольких неизменённых
restore/copy cases также выросли. На хосте мало свободного места и меняется
нагрузка; сравнение полного gate откладывается до выделенного beta окружения.

Ожидаемый skip — live PostgreSQL тест, запускаемый только в назначенное
окно `W54_STAND_COPY_WINDOW=1`. Ни один контейнер или внешний стенд в этом
измерении не запускался. Пять предупреждений относятся к прежней уборке
временных каталогов pytest.
