**How the harness works.** Each probe starts the repository's own entry point,
`infra/deploy/serve.py`, as a child process. The child runs on ports 57500/57501 (overridable with
`W55B_QA_API_PORT` and `W55B_QA_HEALTH_PORT`) with `AUDITMANAGER_PROVIDER_MODE=recorded`. Its
environment carries no key, no proxy and no live mode. The probes talk to it over real sockets, with
credentials minted for real accounts.

- Runs execute through the served application's own in-process dispatcher (`EXECUTION_ROLE` unset,
  so `all`). This is the same path the lanes' journeys use.
- A run whose model request has no recording fails with `analysis_input_invalid`. It never makes a
  live call.
- The harness signals only its own child, after checking `/proc/<pid>/cwd`. If a port is already in
  use, the session fails; the harness never stops another process.

**Expected values are computed independently.** They come from the bundles' own members, using
readers written in `qa_support.py`: a stdlib ZIP reader, a pypdfium2 per-page count, a
`_results.md` body reader and a PNG IHDR reader. No expected value is read back from the product.
No `tests/support/**` file and no other `conftest.py` was edited.

## 4. Findings

### QA-1 — Major: a caller with no valid credential takes upload slots and has its body read and spooled before it is refused

**Probes.** All three are in `tests/integration/qa_w55b/test_p5_upload_gate.py`:

- `test_an_unauthenticated_upload_is_refused_before_its_body_is_read`;
- `test_unauthenticated_callers_cannot_hold_the_upload_slots[no_credential]`;
- `test_unauthenticated_callers_cannot_hold_the_upload_slots[forged_credential]`.

All three are red in the final run and again alone on a freshly migrated database.

**Expected** (the seam is fail-closed, and the gate exists so that a body is not read only to be
refused):

1. An upload with no credential that sends its headers but no body is answered
   `401 authentication_required` within seconds.
2. Two uploads with no credential, or with a credential this deployment did not sign, that stall
   mid-body do not take the deployment's two upload slots. An authenticated upload sent meanwhile is
   answered `201`.

**Observed.**

1. There is no answer within 5 s: the server waits for the body.
2. The authenticated upload is answered `503 dependency_unavailable`
   (`details.dependency: upload_capacity`) in both parameter cases.

**Characterisation** (a scratch script against the same served application; not committed):

- The anonymous body is spooled to a temporary file. After 8 MiB of a declared 64 MiB were sent, the
  API process held one deleted temporary file of 8 388 463 bytes.
- The `401` came 0.18 s after the last declared byte, so the whole body is read first.
- Two stalled anonymous holders kept both slots for at least 60 s. Authenticated uploads were `503`
  at 5, 30 and 60 s. The slots were released on disconnect, after which the next upload was `201`.

**Trace.**

- `src/auditmanager/api/routers/multipart.py:258-268`. `BodyCapMiddleware` takes a slot for any
  `POST` matching `_UPLOAD_ROUTE` (`multipart.py:84`) before anything has looked at the credential.
- `src/auditmanager/api/app.py:425-437`. Authorization is an application-level dependency
  (`build_authorization_dependency`).
- FastAPI's request handler reads the form (`fastapi/routing.py:430`,
  `body = await request.form()`) before it solves dependencies (`:481`). So the seam runs only after
  the whole multipart body has been parsed and spooled.

**What W55b changed.** Bodies were already read before authentication. W55b changed two things:

- the upload cap is now 251 MiB, where it was 26 MiB;
- there is now a two-slot gate that this kind of caller can fill.

**Exposure on the stand (by reading, not run here).**

- `infra/deploy/proxy/nginx.conf:259-269` sets no `proxy_request_buffering off`. So nginx buffers
  the whole body, under `client_body_timeout 120s`, before it proxies the request. A stalled client
  therefore never reaches the API.
- The BFF answers `401` locally when there is no session cookie (`web/src/app/bff/v1/[...path]/route.ts:45`).
- The remaining exposure is `/api/v1/projects/*/documents`. A client with no account can send
  bodies of up to 260 MiB there. Each one is read and spooled by the API, and holds a slot while
  that happens. Repeated in a loop, this keeps legitimate uploads refused with `503` and costs the
  API disk. It is bounded by the attacker's bandwidth, not by authentication.

**Repair (direction only; STREAM's files).** Refuse a missing or unverifiable bearer credential in
`BodyCapMiddleware` before taking a slot or reading the body. A signature-and-expiry check needs no
database read. Leave the full standing check (epoch, archive, roles) where it is. Re-run the three
probes on the repaired SHA.
