# AR-V3-BETA-PACK-STATUS-WEB-FIX-02 — four findings of judge J8 on the previous web fix

An independent judge read `AR-V3-BETA-PACK-STATUS-WEB-FIX-01` and reported four findings. Each was re-proved with a real test run before it was fixed (task file, P-01 to P-04); all four reproduced, and the first is worse than reported. The task is web-only: no contract, backend, generated-client or shared-library change.

## Handoff

- Task: [AR-V3-BETA-PACK-STATUS-WEB-FIX-02](tasks/AR-V3-BETA-PACK-STATUS-WEB-FIX-02.md), frozen from `4e6b0b4d4eeb4fc93d5209db248ed773bf7c3318` (the tip of `integration/ar-close-1026`).
- What changed, by finding:
  1. **A start in flight while the list stops showing the list.** The brief's fix was to keep the control drawn in the loading and error branches. The run showed that is not enough: the control is a different instance in each branch, and TanStack drops a per-call `onSuccess` together with the observer it was given, so even a page that comes back before the answer lost the navigation (task P-01, fourth test). The observer is now held by the run list, which is mounted through every branch: `useArV3GroupStartIntent` also calls `useStartArV3Group()` and returns it as `mutation`, and the control sends and reads through it. The 202 opens the group whichever branch is showing; a refusal that arrives while no control is drawn is on the observer when the control comes back, with its retry under the same key. The loading and error branches also draw the control under their message while a start is pending (so «Дальше» does not hide a request on its way) and nothing more when none is; a fresh visit with no pack draws no control. The deviation from the brief's wording is deliberate and argued in the task file.
  2. **`press` on a disabled button.** `LiveRender.press` returns `Promise<boolean>`; on a button that carries `disabled` it calls nothing and returns `false`. The reproduction is on the unfixed instrument: the button was disabled in the markup and a second press still made a second `startArV3BetaGroup` call (P-02). New `live-render.test.ts` (4 tests) and three live tests: a second press on a pending start is refused and sends nothing; a start that is never answered keeps the button disabled through a pack re-read, a re-render and a list refetch (the shape of an `inFlight` stuck true, asserted by markup); an answered refusal enables the button again. No existing test relied on a disabled press: the 8 stateful tests of the previous lane passed against the new `press` before any assertion of this task was added to them.
  3. **The digest measure.** `longestDigestRun` lower-cases, removes white space, `-`, `_`, `:` and the zero-width characters (and the soft hyphen) between hex characters, and reads the markup twice: as written and with tags removed (a digest cut into sibling elements). A whole digest printed five ways measured 5 to 8 with the old measure (P-03); twenty fixtures now each measure 64, the twelve-character form still measures 12 in either case, and ordinary markup stays under 6.
  4. **`useIsMutating` and a changed version.** `inFlight` is now read with `useSyncExternalStore` over the mutation cache, evaluated for the version of the current render, and `RunList` renders `VersionRunList` with `key={versionUid}` so the observer, the cursor and the key belong to one version. Both were needed: the hook alone leaves the lifted observer's own pending state from version A on the button of B (mutation M4b). Production is unchanged (Next remounts the page on `[version_uid]`); only the live harness's `update()` reached it. The "different key for a different version" test now asserts the second version's button is enabled; two new tests keep the first start pending, which the old one did not.

- Limits:
  - The hook now subscribes to the mutation cache directly, so the pending flag no longer waits for TanStack's notification timer; the window that note recorded in `FIX-01` (a pack re-read that fails between the press and React hearing of it) was not re-measured and is not claimed closed. Its consequence is smaller than before: the observer is held, so the navigation of that start is no longer lost with the control.
  - A refusal that settles while the list is loading is drawn when the control is next drawn (the list back with an installed pack). If the pack stays unreadable and nothing is pending, no control is drawn and the refusal is not shown; it is held on the observer, not shown and not retried silently.
  - The key still lives as long as the run list; a page left and entered again is a new intent (as in `FIX-01`).
  - While a start is pending and the list is loading, the page shows two loading messages (the list's and the request's). That is accurate, not elegant; no style was added.
  - The digest measure does not decode HTML entities; React writes none for the characters it reads through.
  - The stateful tests use a hand-written DOM, not a browser; no stand, pack or credentialed journey was available.
