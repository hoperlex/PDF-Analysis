# План единого визуального языка для 31 экрана

**Статус:** план дальнейшей разработки, 30 октября 2026 года. Демонстрационный `/dashboard` выполнен по `HOTFIX-DASHBOARD-SHOWCASE-INT-20261030`, а общий адаптивный каркас и навигация — по `HOTFIX-SHELL-NAVIGATION-INT-20261030`. Остальные экраны этот документ не объявляет готовыми. Основа инвентаря — 31 файл `web/src/app/**/page.tsx` и соответствующие строки `SCREEN_REGISTRY` на `ee90c6a5`. Перед каждой следующей задачей инвентарь сверяется с новым `origin/dev`.

## Цель и границы

Единый интерфейс для рабочих, сравнительных, справочных и административных сценариев: две согласованные палитры («Светлая» и «Тёмная») и существующий выбор «Как в системе». Референс Hynex задаёт ритм карточек, глубину тёмных поверхностей, спокойные контуры и бирюзовый акцент; графики, медицинские числа, иллюстрации и функции референса не переносятся. Все числа, статусы, ошибки и права продолжают поступать из нынешних источников. Общая навигация использует боковую панель на широком экране и компактное раскрывающееся меню на узком.

Работа рассчитана на **визуальную согласованность**, включая реальные состояния и доступность. Переделка бизнес-сценариев, API, хранения, промптов и моделей в оценку не входит.

## Дизайн-контракт

1. **Токены:** роли для фона приложения, поднятой карточки, вложенной поверхности, текста трёх уровней, линии, акцента, семантических состояний, тени, радиуса, типографики и интервалов. Новые цветовые значения определяются только в `web/src/app/globals.css`: корень, системная тёмная тема и явно выбранная тёмная тема; оба тёмных блока равны. Компоненты читают токены, не задают локальные цветовые литералы. Точные значения фиксируются после пилота `/dashboard` и проверки контраста.
2. **Компоненты:** общий вид страницы, заголовка, панели, карточки, метрики, таблицы, фильтра, поля, кнопки, бейджа, сообщения, модального состояния и пустого результата. Любая новая декоративная графика строится из CSS или из разрешённого собственного ресурса; чужие иллюстрации не копируются.
3. **Иерархия:** на каждом экране одна явная цель и один главный заголовок; первичное действие видно до вторичных; длинные имена проектов и документов переносятся. Число без данных не подменяется нулём, неизвестный статус не окрашивается как известный.
4. **Состояния:** загрузка, пусто, ошибка, запрещено, отключено, ожидание, успех и фокус имеют обе палитры. Цвет сопровождается подписью или формой, чтобы статус читался без различения цвета.
5. **Адаптивность:** проверить ширины 390, 768 и 1440 px. На 390 px панели становятся одной колонкой, широкие таблицы получают управляемую горизонтальную прокрутку внутри панели, а навигация использует существующий компактный режим. Существующие браузерные ограничения каждого сложного экрана измеряются до обещания полной мобильной работы.
6. **Доступность:** минимум WCAG AA для обычного текста (4,5:1), 3:1 для значимых границ и графических индикаторов согласно действующему правилу проекта; видимый клавиатурный фокус, `prefers-reduced-motion`, семантические заголовки, подписи форм и достаточная область нажатия. Обе темы и системный режим проверяются отдельно.

## Приёмка и публикация по этапам

- Для каждого адреса: обе темы и системный выбор, 390/768/1440 px, реальная загрузка/пусто/ошибка и роль, если применимо; длинный русский текст; клавиатура и видимый фокус. Снимки и короткий чек-лист хранятся рядом с отчётом этапа, а не подменяются статическим render-тестом.
- На этапе A устранить уже известное нарушение цветовых литералов в `web/src/_pages/stage-compare/ui/stage-upload-panel.module.css` и 16 ссылок на неопределённые токены в CSS модулей сравнения с явным владением соответствующими путями. Пилот P эти файлы не меняет.
- На каждом этапе: `git diff --check`, typecheck, lint, адресные Vitest; для токенов — `theme.test.ts`, `tokens-defined.test.ts`, `styling-layer.test.ts`, `contrast.test.ts` и avatar-palette при затронутой палитре. Сложные экраны дополнить браузерным проходом состояний. Полный `make gate` выполняется по действующей политике при отдельной публикации в `main`, а не предполагается из публикации в `dev`.
- Каждая задача имеет свой `task_id`, frozen SHA и contract versions, точные `allowed_paths`, один владеющий интеграционный слот для глобальных стилей/оболочки, критерии и rollback. Контракты, миграции, зависимости и backend не входят в визуальную волну.
- Результаты этапов складываются в `origin/dev` проверенными fast-forward коммитами. Если общая палитра ломает чтение конкретного экрана, сначала исправляется тот экран в его слоте; на `main` дизайн попадает только по отдельному прямому указанию владельца и по политике развёртывания.

## Риски и контроль изменений

- Палитра меняет контраст для всего приложения. Сейчас новые токены используют только общая оболочка и `/dashboard`; остальные компоненты получают общие семантические значения лишь после проверки этапа A.
- Таблицы сравнений и длинные юридические тексты могут выйти за ширину 390 px. Для каждого такого места фиксируется отдельный скриншот и способ прокрутки; потеря столбцов или доказательств не допускается.
- Визуальные эффекты референса могут замедлить тяжёлые страницы. Используются лёгкие CSS-слои, без видеозаставок и внешнего шрифта; при `prefers-reduced-motion` анимация сокращается.
- Редизайн не меняет смысл статуса. Источник данных, формулировки ошибок, доступность действия и экспертные решения остаются проверяемыми текущими тестами.

**Откат:** каждый этап — отдельный коммит/ветка; откат этапа не требует миграции данных. Общий дизайн-контракт фиксируется после A; если поздний экран требует нового токена, его добавляет владелец следующего интеграционного слота, а не два параллельных исполнителя.
