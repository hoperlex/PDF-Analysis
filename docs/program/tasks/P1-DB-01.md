# Task P1-DB-01 — provide the PostgreSQL migration and transaction foundation

> **Status: specified; dispatch after accepted `P1-INT-00`.** Authoring may run in
> parallel; final acceptance runs after `P1-INF-01` is integrated.

## Outcome

A clean PostgreSQL database can be migrated and accessed through one typed
session/transaction provider without defining speculative product tables.

## Depends on

- `P1-INT-00` — completed and integrated

## Frozen inputs

- FF-01 and locked database dependencies
- PostgreSQL connection name `DATABASE_URL` and FF-01 lane-isolation variables
- migration head: `none`
- base commit: accepted `P1-INT-00` integration commit

## Allowed paths

- `db/migrations/**`
- `src/auditmanager/shared/db/**`
- DB sections of `src/auditmanager/shared/README.md` and `db/migrations/README.md`
- lane-owned tests under `tests/integration/db/**`
- `docs/program/tasks/P1-DB-01.md` status/handoff

## Forbidden hotspots

- root locks/commands, `infra/local/**`, storage, product bounded contexts, API/web
- contracts, CP-00 artifacts and global styles

## Non-goals

- No Project, DocumentVersion, Run, Finding or Decision schema.
- No generic repository/base service and no automatic retry/outbox.

## Deliverables

- migration configuration and one baseline head
- typed engine/session/transaction construction behind the shared DB boundary
- `src/auditmanager/shared/db/check.py`, proving application connectivity and current
  migration head through the reserved `make check-db` target
- clean-install, current-head and transaction rollback tests against PostgreSQL
- migration documentation

## Required tests

- Command: `make up && make migrate`
  Expected: exit `0` from an empty database in the DB lane's unique instance.
- Command: `make migrate && make check-db`
  Expected: exit `0`; second migration is safe and head is current.
- Command: `.venv/bin/pytest tests/integration/db`
  Expected: exit `0` against PostgreSQL, not SQLite.
- Command: `git diff --check`
  Expected: exit `0`.

## Integration contract

Later migration owners receive a current baseline head and application code receives a
single session/transaction factory. Callers do not execute connection setup themselves.

## Failure/idempotency/security cases

- Invalid/unavailable `DATABASE_URL` fails explicitly.
- Failed transaction rolls back.
- Re-running current migrations changes no domain state.

## Rollback / feature flag

Foundation contains no product data. Revert code/migration before consumers; never drop
a populated database automatically.

## Handoff

- migration head identifier
- changed files and commands/results
- transaction semantics and known driver limitations
