## 1. What changed

### The subject (`web/src/app/bff/session/subject.ts`, new; `store.ts`)

* After a successful exchange the handler calls `getMe` with the minted credential and opens
  the row with `{login, displayLabel, initials, roles, isDefaultCredential, profileComplete}`
  plus `openedAt`/`expiresAt`. `credentialOf` stays the forwarder's only exit.
* `accountFromMe` checks every field against the contract's `Account` types. It refuses the
  whole answer for any of these:
  * a missing or empty `login` or `display_label`;
  * a role outside `ROLE_VALUES`, or a repeated role;
  * a non-boolean `is_default_credential` or `profile_complete`.

  A refused answer is a refused sign-in (`upstream`), never a session with a guessed subject.
* `initials` is derived from `displayLabel`: the first letter of each of the first two words,
  in capitals (`«Петрова А.»` → `ПА`). The contract has no initials field.
* `isDefaultCredential` is the stricter of the exchange's answer and `getMe`'s. Both report
  the same column a moment apart.
* The subject is copied field by field (`accountFields`). A property the caller's object
  carried but the subject does not have — a credential included — never reaches the row, the
  file or `subjectOf`.

### The register file, version 2 (`store.ts`)

* The format is `version: 2`; every subject field is persisted.
* A **version-1 file is replaced at the first read, not read**:
  * a `console.warn` names the file;
  * the file is overwritten at once with an empty version-2 register, so the old credentials
    leave the volume immediately;
  * every reviewer signs in again, once.
* A version-2 row with any field of the wrong type is skipped; the other rows are kept. An
  unknown version is reported and serves no session, as before.
* `openSession(account, credential, lifetime, now?)` is the form the handler uses. The old
  positional form `openSession(login, credential, lifetime, isDefaultCredential, now?)` is
  kept as a TypeScript overload, for one caller this task may not edit (open question 2). It
  fills the restrictive values: no roles, an incomplete profile, and the login as the label.
* `refreshSubject(id, account)` rewrites a live row's subject. It keeps the credential and
  both instants.

### Subject refresh and the upstream 401 (`route.ts`)

* **After a successful `PATCH /me`** through the catch-all, the handler reads `getMe` with
  the held credential and rewrites the row. A refresh that cannot read a subject closes the
  session: the row is deleted, the cookie is cleared on the `PATCH` answer, and the `200`
  itself is left unchanged (open question 3).
* **After a successful password change**, `getMe` is read with the replacement credential,
  and the new row opens with that subject. If `getMe` fails, the old session is closed and
  the reviewer is sent to `/login` with the cookie cleared. This is the existing path for a
  lifetime the tier will not hold.
* **An upstream `401` on a held credential** (an epoch bump: role change, archive or reset)
  does three things in the same answer:
  * deletes the row;
  * clears the cookie;
  * returns the API's own `401` envelope, with the API's correlation id.

  It is not a redirect. Every other status keeps the session.

### Registration (`route.ts`)

* **`POST /bff/v1/registration`** (reserved segment `registration`) forwards
  `submitRegistration` the way the exchange is forwarded: the form is read in this process,
  and the answer's body is never returned.
  * The form fields are `login`, `password`, `confirm_password`, `last_name`, `first_name`
    and the optional `middle_name`.
  * A missing or blank required field, a body that is not a form, or a confirmation that
    differs from the password is answered `validation`. Nothing is sent upstream in those
    cases.
  * A blank `middle_name` is left out of the request body.
  * Success (`201`) → `303 /register/submitted`, with no cookie.
  * Every other answer → `303 /register?refusal=<v>`, where `v` is one of
    `{validation, login_taken, request_pending, queue_full, throttled, upstream}`:
    * `422` → `validation`;
    * `409` with one of the three `conflict_reason`s → that value;
    * `429` → `throttled`;
    * an unconfigured deployment → `upstream`;
    * anything else, including an unknown `conflict_reason` → `upstream`.
  * Any other verb, or any deeper path under `registration`, is `404 not_found` and nothing
    is forwarded.
* **The catch-all refuses the `registrations` first segment**: `404 not_found`, before the
  session is read, with or without a session (open question 1).
* **On a failed exchange (`401`)** the handler calls `readRegistrationStatus` with the same
  pair, presenting the same credential the exchange presented:
  * only a `200` whose body says `status: "pending"` gives `/login?refusal=pending`;
  * a `401` (unknown pair, wrong password, decided request), any other status, a body that is
    not JSON, or a `200` naming anything else gives the generic `credentials`.
  * A successful exchange is never followed by a status read.
* An exchange answered `429` → `throttled` (open question 5).

### The guest throttle (`web/src/app/bff/session/guest-throttle.ts`, new; `web/src/shared/config/proxy-trust.ts`, new)

* A token bucket per client covers both `POST /bff/v1/session` (the exchange only, not
  `/session/end` or `/session/password`) and `POST /bff/v1/registration`.
  * **Parameters:** capacity 10; one token back every 6 s; one bucket per client shared by
    both doors.
  * **When it is checked:** first, before the form or the configuration is read.
  * **When it refuses:** `303` to the door's own screen with `throttled`, and nothing is sent.
* **The key** is `X-Real-IP`, and only under `AUDITMANAGER_BEHIND_PROXY=1`.
  * The flag is read by `isBehindProxy()` in `shared/config/proxy-trust.ts`, the way
    `session-store.ts` reads its variable.
  * It is not re-exported from the barrel and **not** added to `SERVER_ONLY_VARIABLES`.
  * Only the exact value `1` turns the flag on; any other value turns it off, which can only
    tighten the throttle.
  * Without the flag, every request shares one bucket.
  * Behind the proxy, a request with no usable address shares one "unidentified" bucket.
  * `X-Forwarded-For` is never read.
* The table lives in process memory, on `globalThis`, and is bounded at 10 000 clients
  (least recently seen forgotten).

### The refusal sets (`features/sign-in/model/exchange.ts`, `route.ts`)

* `SIGN_IN_REFUSALS` and the handler's `type Refusal` both gain `pending` and `throttled`.
  `web/tests/unit/session/refusal-mirrors.test.ts` reads the union out of the handler's
  source and asserts:
  * the two sets are equal;
  * every value the handler redirects with is one the screen renders, and the reverse.
* `ChangeOutcome` stays the seven values it was (`Exclude<Refusal, 'pending' | 'throttled'>`).
* The two Russian sentences render through the existing `signInRefusalMessage` and
  `SignInForm`.
  * **pending:** «Заявка на регистрацию ещё не рассмотрена: войти можно будет, когда
    администратор её одобрит. Подавать заявку повторно не нужно.»
  * **throttled:** «Слишком много попыток входа и подачи заявок за короткое время. Ничего не
    изменено: подождите немного и попробуйте снова. Это ограничение относится к подключению,
    с которого идут попытки, а не к учётной записи.»
* `app/login/page.tsx` needed no change: it validates through `isSignInRefusal`, so both
  values reach the screen. `login-route.test.ts` asserts that.
* The `W40-LIMIT` header comment in `exchange.ts` is rewritten:
  * the per-**account** throttle is still not named on the screen, and the reason stands;
  * `throttled` is the per-**client** guest bucket, decided before any login is read, so it
    says nothing about any account.

## 4. Risks, known limits and open questions

These are questions, not decisions taken.

1. **The `registrations` refusal also blocks the administrator's three operations.** The
   plan (§3.5), the task file and the brief all say the catch-all refuses the
   `registrations` first segment, as it refuses `auth`, and that is what is built. The same
   segment holds `listRegistrations` (`GET /registrations`), `approveRegistration` and
   `rejectRegistration`, so the browser cannot reach them through `/bff/v1` either. `W50`'s
   admin tile (`pending_total`) and `W51-ADMIN-REQUESTS` call them through this catch-all.
   **Proposed amendment, for the integrator to rule on:** refuse exactly `POST /registrations`
   and every method under `/registrations/status`, and forward the rest with the session's
   credential. That keeps the plan's stated purpose: the two public operations are reachable
   only through the reserved doors. The M1 test would then be narrowed to those two
   addresses, with a control that `GET /registrations` is forwarded. The judge brief
   (`W49-JUDGE-X`) repeats the whole-segment wording too.
2. **Legacy `openSession` overload.** `web/tests/guards/default-credential-screens.guard.test.ts`
   is outside the grant and calls `openSession(login, credential, lifetime, isDefault)`. The
   overload stays for it, with restrictive defaults; the handler never uses it. Whoever next
   owns that guard (`W50`) should move it to the account form and delete the overload.
3. **A failed refresh after `PATCH /me` closes the session** — the fail-closed reading. The
   profile was saved and is reported as saved, and the next request is signed out. The plan
   is silent on a failed refresh; confirm or reverse.
4. **The signing key on unauthenticated forwards.** The exchange, the status read and the
   registration forward present `AUDITMANAGER_API_TOKEN` (the key the API signs with) as a
   bearer on `security: []` operations.
   * For the exchange this predates the task; the handler's comment calls it ignored.
   * The plan's "same credential handling" extends it to the two new forwards.
   * It is the `W37CERT4-3` shape (key material in an `Authorization` header), on the
     internal network only.
   * A follow-up could forward these three without `Authorization`. Not decided here.
5. **An upstream `429` is mapped to `throttled`** on both doors. This is an addition the plan
   does not name. The internal path never passes the proxy, so it only matters if a proxy is
   ever placed between this tier and the API.
6. **Bucket parameters** (10, one per 6 s, shared by both doors per client, 10 000 clients
   tracked, memory per process; a restart forgives every guest) are this task's choice.
   Confirm the numbers. Without the flag, one bucket serves the whole deployment.
7. **The redirect targets do not exist yet.** `/register` and `/register/submitted` are
   `W51`'s, so until then a registration redirect lands on the not-found page with the value
   in the address. No page was created, as briefed.
8. **The registration form contract `W51` must follow.** The field names are listed in §1. A
   confirmation mismatch is `validation`, because the closed set has no `mismatch`.
   `W51-AUTH-01`'s mutation "the password mismatch is caught before the request" is
   satisfied here, in the handler.
9. **`initials` is derived here from `displayLabel`.** `W50`'s `entities/account` helper should
   use the same rule, or read the subject's value.
10. **The frame and `/login` still show `subject.login`.** `layout.tsx` (`W50`) and `/login`
    (`W51`) are unchanged.
