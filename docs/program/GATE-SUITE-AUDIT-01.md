# GATE-SUITE-AUDIT-01 — ревизия состава и стоимости тестов

Задача: `docs/program/tasks/GATE-SUITE-AUDIT-01.md`. Проверяемое дерево:
`5842d01ce9a1a38fe2097dae080f9792c213ff37` на основе
`origin/dev=8069220909e40c39e2329d5f5cb9585a5a5714ec`. Это ревизия
тестов, а не изменение набора полного gate. `R-135` откладывает следующий
полный прогон до интегрированного beta-кандидата.

## Вывод

Числа 2600 backend и 1100 frontend уже не описывают весь текущий набор.
На указанном дереве без выполнения собраны **5661** тест backend battery и
**908** контрактных тестов; foundation собирание через `--collect-only`
преднамеренно запрещает. Последний измеренный foundation прогон содержал
35 тестов. В дереве 400 отслеживаемых Python test-файлов и 137 Vitest-файлов.
Последний доступный полный frontend прогон (W55b) выполнил 2047 тестов.
Это разные SHA и режимы измерения: 2047 нельзя объявлять текущим числом.

Сокращать набор по числу test cases не обосновано. Параметризация одной
проверки по вариантам входа увеличивает счётчик, а дорого обходятся запуск
процессов, повторный рендер экранов, работа с БД и загруженный Docker host.
В первую очередь нужно убрать доказанные повторные вычисления и получить
top-20 `call`/`setup` на следующем полном gate; выпускные проверки реальной
сборки, БД и развёртывания остаются обязательными.

## Измеренные и подтверждённые горячие места

### Frontend: почти всё время самих тестов в пяти файлах

Vitest сообщает время по файлу. В W55b сумма таких времён 32.792 с;
пять файлов заняли 30.051 с (91.6%). В W55a те же пять заняли 24.842
из 26.845 с (92.5%). Это доля **времени файлов**, не полного `npm test`
(47.65 с W55b, включая collection/transform).

| W55b файл | Tests | Время файла | Что выполняется |
| --- | ---: | ---: | --- |
| `web/tests/unit/styles/contrast.test.ts` | 20 | 12.682 с | Контрастная census с реальным рендером экранов, CSS и двумя палитрами; `measured(theme)` уже кэширован, но `everyPair()` напрямую повторяется в нескольких кейсах. |
| `web/tests/guards/query-key-shape.guard.test.ts` | 16 | 7.056 с | `tsc` для негативных/контрольного fixtures и ещё один `tsc --noEmit --incremental false` для всего `web/`; gate-static перед Vitest уже запускает `npm run typecheck`. |
| `web/tests/guards/rendered-language.guard.test.ts` | 26 | 4.180 с | Рендер текста экранов; исторический D-53 показал, что исходный `.tsx/.ts` поиск пропускал составные английские строки. |
| `web/tests/guards/lazy-boundary.guard.test.ts` | 24 | 3.510 с | Рендер экранов и отдельный расчёт контрастной census для доказательства, что lazy wrappers не скрыли пять виджетов. |
| `web/tests/guards/eslint-boundary.guard.test.ts` | 4 | 2.623 с | Четыре отдельных процесса ESLint по негативным и контрольному fixtures. |

`query-key-shape` сохраняет две отдельные гарантии: компилятор отвергает
неверные типы, а gate действительно запускает typecheck до тестов. Удаление
всего guard уничтожило бы первую гарантию. Вероятный выигрыш — убрать
повторный **полный** `tsc` внутри Vitest после доказательства порядка
Makefile, оставив компиляцию негативных/контрольного fixtures и отдельный
typecheck gate. `eslint-boundary` аналогично проверяет, что правила реально
краснеют, в отличие от простого чтения конфигурации; четыре fixtures можно
попробовать передать одному процессу, сохранив проверку каждого rule ID.

### Backend: большой счётчик и доказанная стоимость процесса

`tests/integration/ingest/test_bundle_archive.py` собирает 269 случаев.
Точечный запуск на проверяемом дереве: **269 passed за 15.84 с**; самые
долгие вызовы — проверка уборки временного каталога 2.92 с, производственный
лимит распаковки 0.57 с, константы лимитов 0.42 с, ограничение памяти 0.35 с.
Три набора по 67 негативных архивов заново строят похожий вход и дважды
вызывают продуктовый разборщик: точный отказ, сравнение с независимым
reference validator и очищенное сообщение. Общая подготовка одного архива
на вариант может убрать повторную работу, сохранив все три утверждения и
отдельный oracle. Это кандидат на эксперимент, а не основание выбросить
67 вариантов: они покрывают разные ограничения ZIP и bundle.

`tests/integration/composition/test_stand_copy_refusals.py` собирает 147
случаев, из них 60 проходят реальный shell guard и его копию с удалённым
guard, 38 проверяют грамматику. Запуск с лимитом 55 с выполнил примерно
59/147 случаев и завершился по `timeout` (exit 124), поэтому **успех
файла и его общее время не заявлены**. Это подтверждает высокую стоимость
семейства и необходимость получить полный `--durations=20` на подходящем
host. Подмена `docker`/`ssh` stub здесь проверяет поведение скриптов и
мутацию guard; отдельные проверки реального образа/стенда остаются нужны.

`tests/integration/db/conftest.py` уже устраняет грубый повтор: один
session-scoped `migrated_template` применяет буквальный Alembic command;
обычные тесты получают изолированный `CREATE DATABASE ... TEMPLATE` клон.
`empty_database` намеренно остаётся пустой для проверки установки миграций
с нуля. Общая БД между тестами нарушит изоляцию и не является предложением.

## Очередь задач по снижению стоимости

| Приоритет | Изменение в отдельной задаче | Обязательное доказательство |
| --- | --- | --- |
| 1 | На следующем разрешённом полном gate сохранить `GATE TIMING` и добавленный `--durations=20` для contract, foundation и обеих частей battery; приложить точный SHA, нагрузку host и список top-20 `call`/`setup`. | Исключить время ожидания Docker/S3 и повторные инфраструктурные отказы из оценок стоимости теста. Сравнивать одинаковые SHA/stand/порядок. |
| 2 | Устранить повторный полный `tsc` внутри `query-key-shape`, кэшировать неизменяемые результаты census в `contrast`, измерить четыре ESLint fixtures одним процессом. | Негативные и контрольные fixtures краснеют/зеленеют как раньше, Makefile сохраняет fail-fast typecheck, census всё ещё открывает все экраны и обе палитры. Повторить Vitest до/после. |
| 3 | Прототип общей подготовки для трёх 67-элементных семейств в `test_bundle_archive.py`; отдельно профилировать shell-guard семейства `composition`. | Все 269 случаев/их утверждения и reference oracle сохраняются; причины отказа и отрицательные мутации совпадают; время файла уменьшается на одинаковом SHA/host. |
| 4 | По top-20 backend gate решить, нужны ли дополнительные фикстуры, batching subprocess или осторожная параллельность независимых семейств. | Реальная сборка образов, fresh migration, изоляция DB/S3 и deploy сценарии остаются; при параллельности нет гонки за daemon/ports и нет потери детерминизма. |

Цель — сократить wall time полного gate при том же наборе релизных
утверждений. Само уменьшение числа test cases не метрика успеха. `gate-fast`
и `gate-affected` ускоряют цикл разработки, но их маркеры не заменяют
буквальный `GATE OK` интегрированного SHA.

## Дополнение 2026-10-15 — предложение по измерению принято к handoff

Владелец поддержал измерение перед решением о сокращении или перестройке
тестов. Это план для отдельного beta-gate и последующих оптимизационных задач,
а не результат полного gate на текущем дереве.

1. После последнего кодового блока зафиксировать один точный чистый beta SHA.
   Записать полный SHA, команду, exit status, состояние памяти и свободного
   места до запуска, а также условия ожидания gate slot/Docker/S3.
2. Выполнить полный `make gate` и сохранить целиком его лог. В итоговой сводке
   выписать все строки `GATE TIMING`, top-20 `setup`/`call` из каждого
   `--durations=20` для contract, foundation и обеих частей battery, а также
   времена frontend-файлов. Отдельно указать `GATE OK` или точный отказ.
   Ожидание slot и инфраструктурный сбой не записывать как стоимость теста.
3. Для дорогих семейств составить карту «требование → проверка → отрицательный
   пример/независимый oracle». Сравнивать время подготовки, вызова и всего
   файла; число случаев использовать как описание объёма, а не показатель
   полезности или скорости.
4. Каждую оптимизацию оформить отдельной задачей с владением test/fixture
   paths. До/после измерять на двух названных SHA при одинаковом product code,
   сопоставимых host/нагрузке и одном порядке запуска. Принимать изменение
   только при сохранении проверяемых требований, отрицательных мутаций,
   изоляции DB/S3 и релизных проверок реальной сборки/развёртывания.
5. Любая правка после baseline создаёт новый кандидат. На окончательном SHA
   повторить полный gate; ускорение локального tier и число удалённых случаев
   не заменяют буквальный `GATE OK`.

Первым блокером измерения остаётся красная programme governance suite: шесть
прежних `W56A-*` task-файлов требуют своих владельцев. Полный gate на финальном
beta SHA нельзя объявить успешным, пока это не исправлено и не перепроверено.

## Проверки, ограничения и handoff

- На текущем дереве выполнены read-only inventory и сборы: 5661 battery,
  908 contract; foundation законно отказал `--collect-only`.
- Точечный backend запуск: 269 passed / 15.84 с с `--durations=20`;
  Pytest выдал пять предупреждений об уборке временных каталогов.
- Точечный stand-copy запуск ограничен 55 с, exit 124 после частичного
  прогресса; результатов `passed` для файла нет.
- Frontend измерен только по историческим логам: в рабочем дереве нет
  `web/node_modules`. Полный gate не запускался по `R-135`; локальный
  Docker также ограничен sandbox/snap, см. `GATE-OPT-01.md`.
- Изменены только этот отчёт и task-файл. Contracts, тесты, fixtures,
  Makefile, migrations, root dependencies, composition roots, global styles,
  refs и runtime код не менялись этой задачей. Нет feature flag и изменения
  поведения; rollback — revert двух документов.
- Интегратору: сначала интегрировать `GATE-OPT-01` (Makefile slot), затем
  этот аудит; последующие оптимизации оформить отдельными task IDs с
  владением конкретными test/fixture paths. На final beta SHA собрать
  полноценный baseline и только после него назначать сокращения или
  параллелизм. Не выдавать частичный `gate-affected` за `GATE OK`.
